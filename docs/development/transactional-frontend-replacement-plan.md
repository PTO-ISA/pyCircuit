# 事务级前端与 ACIR 逐步替换计划

日期：2026-10-27。状态：实施计划，尚不表示迁移完成或本候选测试通过。

语义依据为 [issue #361 的本地设计文档](https://github.com/PTO-ISA/pyCircuit/blob/main/issue/transactional-frontend-acir.md)及用户后续确认。本文规定如何替换、复用、迁移和验收，不重新定义未决语言语义，也不修改冻结的历史批准记录。

## 1. 目标与工程原则

将当前前端分析逐步替换为产生规范化事务级 ACIR 的实现，统一资源身份、Rule 原子性和 Method 调用语义，尽量复用现有后端。最终只有一条前端语义路径；直接事务级 t-gfsim 与物理后端是同一公共语义的不同生成目标。

优先覆盖没有同拍状态前递、容量借用或执行顺序依赖的场景。复杂同拍依赖以后可以在框架上扩展；timer 暂缓。不能用扩大首轮范围来推迟最小闭环，也不能把首轮未实现能力宣布为永久取消。

工程原则：

1. **按新语义替换，不以旧测试全绿为设计约束。** 旧功能变化或取消时可以重写、退役对应用例；新设计仍需要的功能失败则是实现缺口或回归。
2. **每块能力贯穿整个编译链。** 同时处理 ACIR、分析、lowering、源码入口、例子、测试与旧路径删除，不长期保留“前端接受、后端无法执行”的形式。
3. **优先复用已验证的基础能力。** 类型、四态运算、资源内核、发布机制和后端可复用；依赖旧候选版本的分析需要改写，不因文件可复用而保留旧语义。
4. **不增加第三套前端。** 实验分支是待审查的原型。迁移期不做失败 fallback，不按例子名称、源码形状或常量选择编译器。
5. **普通设计代码表达算法、状态与连接。** 不让作者补写编译器应推导的 ready/fire、物理寄存器接口或跨模块转发包装。
6. **保持可审阅的证据。** 每批记录源代码、ACIR、公共分析结果、后端产物、独立预期和真实结果。删测、跳过和旧分支 PASS 都不能充当新路径通过证据。
7. **未说明不等于取消，旧支持也不等于必须原样保留。** 对新设计未覆盖的旧能力逐项评估：语义明确且兼容的能力继续迁移；需要新语义选择的部分先讨论。未经确认，不得直接删除，也不得以兼容为由引入隐式语义。具体处理见第 8 节。

这些原则仅覆盖本次替换。旧文档描述当前实现的地方仍可作为基线资料，但与目标语义冲突时不能反过来约束迁移；活跃文档随实际支持更新，不能提前宣称实现。

## 2. 已有基础与不能直接继承的部分

本次评估时的主线是 `b986bb0ad721bc0834a71fc710dddca4bde339f4`。已有原型分支 `feat/transactional-acir-gfsim` 位于 `a3c337b7d43bbefabbe6b763f6595c92986715cb`，基于较早主线 `16453e2b`。实施开始时必须重新记录实际 base/head 和共享工作区状态，不能假定这些版本未变化。

原型已经具备显式 `transactional-v1` profile、原生 Python importer、独立 source unit/link、资源与事务分析、直接 t-gfsim 生成及有限旧 C++/RTL 适配。已有历史执行记录，但必须在拟集成候选上重建和复测；不复制另一 checkout 的二进制或生成物作为验收。

**可行性实验已经完成，接下来直接逐步修改正式编译流程。** 本计划不再设置独立实验、另起原型或完整重做最小编译器作为前置门槛。差异盘点只服务于当前待修改的部分；后续编译和仿真是修改后的回归验证，不是重新论证这条路线是否可行。

| 原型部分 | 初始处理建议 | 需要核对的差异 |
| --- | --- | --- |
| `TransactionalPythonImport`、表达式/语句 lowering | 按功能审查后迁入正式所有者 | 不长期与原 importer 并列成为两个产品前端 |
| 资源类型、Module 引用、独立 link | 复用思路和正确实现 | 默认输出 Queue 应在连接父层分配；导出 State 保持原身份 |
| `TransactionalAnalysis` | 作为公共分析的起点 | old-Q、路径相关准入、别名、冲突证明和不可用值必须满足新契约 |
| `TransactionalEmitGfsim` 与 Runtime | 复用并验证 | 调用位置特化的 Query/Effect、资源生命周期及函数组织仍需审查，不宣称已有稳定 Method ABI |
| `TransactionalLowerPhysical` | 用作适配实验参考 | 当前直接生成 physical final；尚未证明符合目标 Routed 锚点接入流程 |
| 现有旧后端适配 | 保留成功的小场景，补缺口 | assert/log、动态未知控制、逐源目录发布等不能因原型拒绝而永久取消 |

| 原型中的 `ac.transaction` 与通用打印 | 需要规范化 | 目标保留事务 Rule 定义/注册，不额外包裹一次 Rule 调用；IR 要便于人读 |

不整体照搬分支附带的设计文档或验收结论。代码复用应逐项证明与当前 issue 一致；实验文档中的限制不是新的语言决定。

## 3. 目标编译边界

```text
Python 薄捕获：只记录语法与来源，不执行设计
  → 未链接事务 ACIR：定义、资源约束、方法要求、组合计算与注册路径
  → link：解析完整闭包、绑定实例与资源、具体化并保留所有权
  → 已链接事务 ACIR：仍保留 Rule/Method/guard/call
  → 公共事务分析：依赖、可用性、fire、更新提议、访问冲突
      ├─ 事务级 t-gfsim：模块组合准备、事务执行、检查、统一提交
      └─ 路由适配及对应性验证
          → Routed ACIR 锚点
          → Hardware final
          → 现有 C++ / RTL 发射器
```

公共分析由 MLIR 层拥有。两个生成方向不得各自解释资源准入、Method guard 或更新冲突。分析结果只对其对应的不可变 IR 快照有效，IR 改动后应重新计算。

以下内容必须在物理 lowering 前保留：资源身份与所有者、实例绑定、Rule 事务边界、Method 接口与调用、guard 与分支路径、数据值和效果的关系。物理引脚、寄存器 kernel 和 Work 调度不是前端需要提供的内容。

规范化 ACIR 的普通打印应直接呈现这些概念。位置、来源和认证信息不能丢失，但可以提供紧凑的默认展示及完整调试 dump；不能把认证信息藏成无法保存/重载的运行时旁路，也不能靠删除语义信息获得“可读性”。

### P0：随首批修改完成必要盘点

输入：新 issue、当前主线、实验分支及现有测试/example 清单。

工作：

- 核对实验分支与新设计的差异，给每个组件标记复用、改写、替换或暂不迁移。
- 建立用例清单，记录原测试目的、所属能力、旧路径、独立 oracle 和迁移批次。
- 在同一 checkout 的已知工具环境中取得最小相关基线；未运行的用例明确记录 NOT RUN，不强制先跑全量 nightly。
- 列出未决语义及其阻塞范围，见第 8 节。已经确认的 old-Q、显式 Rule 注册等不再作为兼容性选择重新讨论。
- 为每批确定负责层、文件范围、依赖、删除范围与最小执行检查。实施、独立测试和审查按项目治理分工。

交付：差异清单、用例迁移清单、候选身份和首批工作包。先覆盖当前批次并随迁移补充，不要求先完整盘点所有功能才能动代码，也不单独重做可行性实验。

退出条件：能分清“旧语义被替换”和“新功能尚未实现”，并能指出原型哪些结论还没有当前候选证据。

### P1：在正式 IR 所有者中规范化现有原型

输入：P0 当前批次语义清单与实验分支已有 IR/验证器。直接修改正式实现并迁入可复用部分；手写 ACIR 仅作为现有 IR 测试，不建立独立实验编译路线。

工作：

- 确定 Module、事务 Rule、Rule 注册、Method、guard/body、资源引用、实例引用及连接的正式表示。
- 区分 payload、资源、静态模块引用；区分未链接与已链接阶段。不能把新事务 Rule 误当当前 `Pure` 组合 `ac.rule`。
- 为未定 primitive 保留实际读写效果的可能性；在 link 确定之前不能将 read 作为无副作用数据读取消除。
- 定义解析/打印、类型和签名、纯 guard、作用域、资源所有权与阶段合法性检查。将 link 才能判定的事实留到 link，不在独立编译时猜测。
- 明确 source-unit、保存产物和缓存的契约身份，拒绝新旧格式或语义的静默混用。旧产物必要时要求从源码重新生成。

最小检查：打印重读稳定；State/Queue 引用与普通值不能混用；非法效果进入 guard 被拒绝；未链接占位符不能直接交给执行后端。

退出条件：可以用可读的 ACIR 描述单寄存器事务，并独立解释其资源、guard、旧值和写入提议。

### P2：替换公共分析并修正后端接入

输入：P1 规范化后的 IR 与实验分支已有分析/适配器。直接迁移和修正，不重新从零搭建闭环；随当前能力的改动执行回归，不等待完整泛型 link 或全部前端能力。

首片范围：单 Module、State、一个带 guard 的 Rule、纯计算、一次更新。随后增加两个独立 State、冲突拒绝以及系统失败检查。

工作：

- 从原型复用或修正实际实例/资源身份、old-Q 读取、路径与更新提议分析。
- 建立最小路由适配，把新分析结果转换为锚点所需的计算、状态更新、使能和连线。
- 更新从事务分析到路由结果的对应性验证。不能简单生成旧 `ac.transaction` 后调用旧候选 SSA，也不能移除旧认证检查而不提供新依据。
- 继续复用锚点之后的存储细化和现有 C++/RTL emitter。适配遇到困难时保留最小失败，再决定改写哪个所有者。
- 原型直接生成 final 的方式可提供实现参考和历史对照；直接修正正式路由边界，不另建实验，也不把原型能力冒充已完成 Routed 接入和保存/重载支持。

验收：手工推导的连续更新、guard 为假保持、回绕、初始化/复位在生成 C++/RTL 中一致；写后读旧 Q、实际冲突被拒绝；检查失败后全系统零提交。四态 payload 和控制检查分开测试，未知控制行为先按第 8 节确认。

退出条件：新 IR 到既有后端不是只“能生成”，而是有真实执行证据。若诊断路径尚未接通，记录阶段缺口，不能宣称这一阶段完整验收。

### P3：逐步替换正式 Python compile/link 与对应例子

输入：P1/P2 对应当前批次的 IR、分析与适配修改，以及实验分支已有 Python/独立单元实现。与这些改动协调推进，不要求另做一轮手写 IR 实验才开始前端替换。

工作：

- 让 Python 经薄捕获和新的原生分析产生同样的规范化 IR，先覆盖计数器及简单状态控制。
- 普通 Rule 显式注册；autorule 在进入公共分析前转换为普通 Rule 加一次注册。
- 独立 compile 发布 body/interface；link 只使用显式提供的闭包解析定义、资源约束和模块引用。消费者编译不重新读取提供者 Python 或 body。
- 将当前正式 compile/link 所有者逐步接到新分析，而不是继续追加第三个 importer。
- 明确每个迁移入口使用的契约。过渡期显式版本选择可用于旧基线比较，但不得在新编译失败时回退，不得根据例子名称或推测的语法自动分流。
- 迁移对应例子、测试、构建入口和文档；删除这一能力不再需要的旧入口。共享的类型/运算/发布代码不因属于旧文件而被误删。

验收：Python 到 C++/RTL 的完整闭环；分文件编译；缺失或不匹配接口拒绝；失败不覆盖已有产物；生成 System 测试不把时钟、提交和转发责任转嫁给 DUT 作者。

退出条件：至少一个真实例子全部走新语义，且可以从其 Python 逐段追踪到规范化 ACIR、分析结果和执行结果。

PR-06b 已提前承担批次 D 的最小引用绑定与跨 owner 提交部分；后续 D 扩展跨层导出、资源别名与共享资源场景，不重复实现这套绑定和最终 fire 分析。该工作包拆分不是通过或合并证据；实际结果见活跃替换状态文档。

### P4：按能力扩展，每批迁移对应例子和测试

| 批次 | 能力与分析工作 | 例子方向 | 必须验证的行为 |
| --- | --- | --- | --- |
| A | 多状态、多 Rule、guard、模块 if/else、冲突检查 | 计数器、状态机 | 每拍读旧状态；条件为真但阻塞不进入 else；独立 if 不隐含优先级；互斥写可接受，不能证明则拒绝 |
| B | 本地 Value/Action/ActionValue、嵌套 Method | 累加器 | 参数按值，不隐式写回实参；新 SSA 返回值可传递；后续 guard 失败时整个事务保持 |

### P5：收敛直接事务级 t-gfsim

依赖 P1/P2 的公共 IR 与分析；可随 P3/P4 的能力同步推进，不必等所有旧例子完成，也不必从零重写实验分支已有 Runtime。

工作：

- 审查并复用原型的准入求值、Query/Effect 和提交机制，所有普通状态读旧 Q。
- 每个逻辑周期先清理提议、完成所需组合准备，再执行已获准的事务效果，全局检查成功后提交。Method 参数相关计算留在方法求值路径。
- 保持 Module、资源唯一所有者及 Rule/Method 的可追踪关系；当前调用位置特化是否保留属于实现选择，不擅自宣称稳定公开 ABI 或计算共享保证。
- t-gfsim 与物理降低复用同一公共语义分析；不得各自推导不同的 fire、冲突或可用性。
- 核对完整周期与旧采样 epoch 的对应、Reset、日志发布、失败恢复和 System 包装。比较结果时明确采用什么周期边界。
- 验证 Runtime-only 安装和外部消费不依赖 LLVM；保留现有发布保护与产物清单机制。

验收：计数器、阻塞 Queue、跨 owner 事务和批处理在直接 t-gfsim、旧后端适配及独立模型之间逐周期一致；四态和失败场景单独检查。不能只比较最终校验和。

### P6：完成生产路径切换与删除

进入条件：已列明的新支持范围有执行证据，剩余能力有明确的迁移/暂缓/退役状态。支持范围外应清晰拒绝，不由兼容路径偷偷处理。

工作：

- 将正式入口统一到新前端分析，移除旧 profile 分流、旧候选值/可写 Method 形参路径及仅服务于旧语义的验证元数据。
- 清理 CLI、CMake、安装清单、脚本、文档和测试里的旧入口。一个旧文件中的通用基础代码可拆出保留；删除范围按依赖而非文件名确定。
- 将公共 C++/RTL 目录发布、真实入口/端口与逐源 provenance 接通，不能长期只提供原型 `--format source` 演示。
- 验证 Routed 保存/重载和 final 生成的契约。旧保存产物如果不兼容，应版本拒绝并说明重新生成方式。
- 核对例子目录、测试选择和 CI 文档。更新后的 gate 必须仍覆盖新设计要求的基础不变量，不通过删掉失败条目伪造全绿。
- 根据实际能力同步语言指南、技能引用和 AGENTS 中的过渡提示；保留历史记录，移除容易重新引入旧语义的活跃指引。

退出条件：只有一条生产前端；两个生成方向使用同一已验证事务语义；迁移清单无无解释条目；规定的新验收通过，未完成工作和未运行检查仍明确公开。

## 5. Example 重写方法

每个例子先写一份简短的“保留行为”说明：输入/输出、计算功能、状态、阻塞条件、原子提交集合、顺序要求，以及哪些周期差异由新语义引起。

按以下顺序重写：

1. 重新选择资源接口：哪一层建立 Queue，哪些输出导出现有 State，哪些参数是实例引用。
2. 以一次完整事务为单位组织 Rule；独立功能分开，必须一起提交的效果不拆开。
3. 将公开组件操作组织为 Method；普通 Rule 显式注册或使用 autorule。
4. 将依赖候选状态的计算改为显式局部 SSA 计算及返回，不恢复状态前递。
5. 按新 Queue 容量规则重审算法。满 Queue 内同事务 pop+push 会整体阻塞，不能只修改预期延迟而忽略可能的停滞。
6. 让编译器承担资源准入和可用性；去掉已被等价推导覆盖的手写协议检查，实际算法条件仍保留。
7. 用独立模型验证数值、消费/输出次数、顺序和阻塞保持，再核对周期差异。

不能为了迁移通过而新增无意义 holding register、单字段 payload wrapper、ready/valid 转发层，或把物理 DFF/clock/reset 接口暴露给普通 DUT。专门验证 primitive 的测试保留其明确用途，不作为普通例子的写法。

若新语义必然改变旧功能的周期行为，在说明中记录原行为、新行为及依据。若连功能目标都需要改变，应先讨论，而不是继续沿用原例子名称和完成声明。

| 类别 | 迁移要求 |

实际执行结果与处理状态是两个字段。建议清单包含：

```text

语义依据 / 原语义与目标语义差异 / 计划批次

基线 revision + 本地内容身份 / 命令 / PASS|FAIL|NOT RUN / evidence
候选 revision + 本地内容身份 / 命令 / PASS|FAIL|NOT RUN / evidence
处理状态：待迁移、已迁移、待实现、待明确语义、待决定、暂缓、已退役

```

原型已有迁移清单可作为输入，但不能直接复制其 PASS 为新候选结果。跳过信息如实保留；未执行部分不算 PASS。测试不能依赖本地管理日志或审查记录才能运行。

每个事务能力至少核对成功、阻塞和非法使用；有状态效果时核对 Reset 与失败零提交；有跨模块和资源输出时核对所有权、唯一提交、消费次数及背压。断言是否触发不能仅靠最终结果碰巧正确来证明。

## 8. 未决事项与暂停范围

### 新设计未覆盖的旧能力

新设计不是完整的旧功能清单。遇到原 pyCircuit 能表达、但新设计没有说明的能力，按以下规则处理：

| 情况 | 处理 |
| --- | --- |
| 不受新语义影响的基础能力 | 默认保留并复用，例如位运算、布局、四态数据运算；验证原契约仍成立 |
| 能直接纳入新框架且含义明确 | 按原功能迁移并保留独立测试，不必为常规实现选择重新请求语义确认 |
| 与已确认的新语义明确冲突 | 按新语义改写，记录行为变化和用例处理，不恢复旧行为 |
| 存在多种合理含义，迁移需要新的语义选择 | 记录为待明确语义，与用户讨论后处理，不自行兼容或删除 |

需要讨论时提供最小、具体的问题说明：原行为及依据、依赖它的例子/测试、能否映射到新资源/Method/事务模型、必须决定的时序或状态含义、可选方案、推荐方案及影响。例如 Memory 未被详细定义，不能据此取消，也不能直接继承旧读写时序；应逐项说明延迟、读写冲突和事务效果如何接入。

**语义已明确、编译器还不会处理，是实现缺口；硬件含义尚有不同合理选择，才是语义缺口。** 前者进入实施任务，后者进入待明确语义清单。不要用反复询问代替常规实现，也不要把实现困难包装成功能取消。

决定之前保留原测试和独立预期，只暂停依赖该决定的迁移工作，其余工作继续。新路径暂不能表达时给出明确诊断，不使用隐藏 fallback，不把旧路径的结果计作新路径通过。讨论结果记录后，再更新设计、用例状态和所属实施批次。

### 当前已识别的未决点

以下问题不得由兼容代码暗中决定；只阻塞依赖该决定的部分，其余已明确工作继续推进。

| 问题 | 需要明确的内容 | 受影响范围 |
| --- | --- | --- |
| 四态 guard 的检查顺序 | 先 X 后 false 与先 false 后 X 是否不同；检查路径与纯条件合并的关系 | 动态未知控制、诊断、全局失败测试 |
| 事务内部再调用 Rule | 是否允许、如果允许其注册和事务边界是什么；Method 嵌套调用已明确 | 旧 callable 复用与相关源码接纳 |
| 多写证明粒度 | Struct 字段、Table 元素等何时可证明互斥或不重叠 | 复杂状态迁移；初期保守拒绝要标记限制，不能作为永久语义 |
| 完整周期与旧采样接口 | 旧半拍/显式样本如何保留、适配或退役；复位和观察对应什么边界 | System 驱动、时间戳、跨目标比较 |
| 尚未明确去留的高级能力 | 依据用例目的逐项决定保留、暂缓或取消 | 大例子和历史测试，不能因原型缺失而自动删除 |

已经确认的默认深度 2、旧占用准入、old-Q、父层 Queue 所有权、普通 Rule 显式注册和 Method 参数按值，不属于这里的待选项。
