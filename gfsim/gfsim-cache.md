# GFSim Rule 执行缓存与按需重试

## 文档定位

本文整理 GFSim 执行过程中减少重复计算的优化思路，作为后续设计和 review 的讨论记录，不代表当前框架已经实现，也不要求现在实现。

基础对象与调用关系见 [module.md](module.md)、[rule.md](rule.md)、[queue.md](queue.md)，仲裁备选见 [schedule.md](schedule.md)。基础方案规定失败清理 proposal、再次激活重算 Work；本文探索在其上增加完整候选缓存、双向等待记录和跨 tick 有效性判断，不属于本版基础流程。

A/B 尚未选定。缓存不自动改变所选容量政策；若采用 B，仍须遵守消费者先行的拓扑仲裁和统一 Xfer。改变调度顺序或取消拓扑约束需要另行论证。

缓存应替代重复的 Work 计算，不能省略资源预约、改变 Queue 数据可见性或复用已失效的计算结果。仲裁优先级和参与规则仍需明确；缓存本身不保证不同调度顺序的逐 cycle 行为相同。

## 优化目标

- Rule 因资源暂不可用而失败时，尽量保留已经完成的计算，不反复 Work。
- 资源变化时，只检查相关等待者，不扫描全部 rules，也不提前执行整条潜在上游链。
- 资源状态由 Queue 维护，rule 通过引用查询，不复制一份 ready 状态再进行同步。
- 当输入、计算依赖和操作目标仍然有效时，允许未获准候选跨 tick 保留。

收益来自减少计算、候选构造和无关检查；代价包括缓存占用、等待关系维护、有效性检查以及 delta 批次的同步。是否值得采用、采用到何种程度，后续用实际负载评估。

## 基础执行边界

Module Work 决定调用哪些 rule，所有实际尝试进入仲裁收尾；`complete=false` 的部分 proposal 必须清理。基础 [RuleSlot](rule.md) 按 RuleId 复用，只保存当前尝试信息，不是跨 tick 候选缓存。若采用本优化，需另建有有效性检查的缓存记录；不能把旧槽位内容或时间戳直接当作可重用候选。Proposal 仍保存在 Queue 来源槽位，其延长生命周期和清理顺序需单独验证。

若想跳过 module 控制逻辑复用候选，必须证明该控制路径及读取依赖仍有效，不能绕过新分支选择。缓存不改变 Queue 的单 push/单 pop 和已获准状态的可见性。

## 两类 Queue 状态

| 状态 | 用途 | 更新时机 |
| --- | --- | --- |
| current 数据、avail/full | Work 的读取和业务计算 | tick 末统一 Xfer |
| 仲裁资格，如 canPush、消费机会是否占用 | 判断本次候选是否值得重试、执行预约 | 同 tick 的仲裁过程中 |

方案 B 中，push 可用性的概念示意为：

```cpp
canPush = !pushOccupied
       && (!currentFull || hasAcceptedPop);
```

这不是完整的预约实现；同一 rule 对同一 Queue 的整组操作仍由 Queue 联合判断，自身 pop/push 的局部容量政策另行确定。方案 A 不使用其他 firing 的 accepted pop 提供空间。

Current 的 full 在本 tick 内可以一直为真，而 accepted pop 已使 canPush 变为真。规则读取的是对应操作的仲裁资格，不能用 current.full 代替。

只有整条 rule 完成 accept 后，才公开其获准效果并通知相关等待者。临时预约不是有效 pop，不提供空间。Accepted push 不使新数据在本 tick 内可读。

## Work 确定实际资源需求

不在执行前要求所有声明的 I/O 都 ready。Work 根据业务分支确定本次真正发生的操作：

```text
正常 completion：pop input + revise register + push output
过期 completion：pop input
```

Output 满不能阻止只丢弃过期输入的 firing。不同分支可能使用不同输入、输出和内部 Queue，因此候选资源列表必须来自实际操作。

所需输入没有数据时，Work 保持 complete=false，已有部分 proposal 交给本批 Arbitrate 清理，后续等待正常读取依赖通知。Work 不自行 cancel，不缓存未完成计算。Peek 成功也不意味着消费机会已经预约：多个 rule 可能读取同一个 current 队首，仍需仲裁单 pop 机会。

Propose 可以同时登记 rule 本次操作的 Queue 引用，按 Queue 身份去重。一个 Queue 上同一来源的 pop/push/revise 作为整组操作检查。

内部状态通常以单元素 Queue 的 revise 表达，但不能因此省略其合法性和必要预约。内部值变化也可能使计算失效，仍属于读取依赖通知的范围。

## 双向等待表

### Rule 表

Rule 表分为固定注册信息和可变执行记录。

| 信息 | 作用 |
| --- | --- |
| RuleId、所属 ModuleId、rule 计算与仲裁入口 | 定位候选；基础 Work 由所属 module 的控制流调用 |
| 执行状态 | 尚未计算、候选等待、待仲裁、已获准等 |
| 实际候选 Queue 引用列表 | 找到本次真实操作，不复制 proposal 数据 |
| 当前等待的 Queue 集合 | 最近一次检查中，哪些资源尚未满足 |
| 计算依赖与目标的有效性信息 | 判断缓存是否还能复用 |

资源引用可以保持只读，执行状态和等待集合需要更新。等待集合是最近一次检查的结果，不要求始终精确同步所有资源变化。

### Queue 表

Queue 保存自己的状态、proposal 和预约，并提供反向等待索引：

```text
Queue Q → 正在等待 Q 的 RuleId 集合
```

阻塞原因的详细分类不是初版必需项；可以先保留 Queue 引用和按本次 proposal 查询就绪的能力。后续若需要更精准的通知，再增加原因或操作类别。

正常读取依赖通知仍需保留。等待表负责已形成候选的资源重试，不能替代输入、内部状态、业务条件变化带来的 Work 唤醒。

## 激活与重试

运行时区分 Module Work 任务、rule 等待检查任务和 rule 仲裁任务。前者按 ModuleId 去重，后两者按 RuleId 去重；缓存不能绕过所属 module 控制路径的有效性判断。

1. 输入、内部状态变化或延迟事件触发正常唤醒。没有有效缓存时执行 Work；有缓存时先检查有效性。
2. Work 形成完整候选后，检查本次实际 Queue 操作。无阻塞时加入仲裁集合，否则建立双向等待关系。
3. Queue 的相关状态变化，将其等待者加入检查集合，不立即递归执行。
4. 检查等待者的资源引用；就绪的等待项可移除。等待集合为空时，加入后续仲裁任务。
5. 最终仲裁仍重新预约全部实际资源。全部成功则 accept、移除等待关系；任意失败则释放所有临时预约、保留候选，并重建等待集合。

一个此前可用的资源可能已被其他 rule 占用，所以“等待集合为空”只表示值得尝试，不保证获准。重试不能仅预约上次失败的 Queue，因为此前成功取得的预约已经释放。

在当前单 push/单 pop、无新数据穿透的设计中，其他 rule 已获准的 pop 是本拍解除上游容量等待的来源。Push 占用写入机会，pop 占用消费机会，也可能使其他候选无法获准，但不会通过新数据同拍唤醒下游。

仲裁串行且单条 rule 的预约、accept/cancel 之间不插入其他仲裁，因此临时预约的建立和释放不必作为其他 rule 的同拍通知源。字段竞争等未定义问题仍按基础方案的支持边界处理，不由缓存表解决。

## Pending：释放预约，保留计算

需要区分三个操作：

- **释放预约**：整体预约失败时，释放该 rule 在所有相关 Queue 上取得的临时预约，候选内容保留。
- **Accept**：所有预约成功后统一确认，获准结果本 tick 不再撤回。
- **废弃候选**：缓存失效、明确放弃或候选已提交后，清理 proposal 和等待关系。

Pending 不持有端口或其他临时预约，避免等待期间占住资源。既有 cancel 如果同时删除候选和释放预约，需要拆分职责，或另设保留候选的失败处理入口。

## 用 (tick, delta) 推进同拍重试

Tick 表示硬件周期。Delta 表示同一 tick 内的执行和仲裁推进批次，不表示一次额外的电路状态提交。

```text
delta 0：直接被唤醒的 C 执行 Work 并整体获准 pop Q2
    → Q2 的仲裁资格更新，通知等待者 B

delta 1：B 有有效候选则重试仲裁，否则先 Work
    → B 整体获准 pop Q1，通知等待者 A

delta 2：A 使用 Q1 的仲裁资格，尝试整体获准

没有可继续处理的任务
    → 所有涉及 Queue 统一 Xfer
```

每个 delta 可以有并行 module Work 批次，屏障后按所选方案的顺序仲裁；方案 B 仍要求消费先行拓扑序，无依赖候选按固定竞争优先级。后续 delta 只查询新仲裁资格，仍读取同一份 current。每个 Queue 每 tick 只 Xfer 一次，顺序为 revise → pop → push；全部 Xfer 完成后才开始读取新 current。

不在每个 delta 执行 Xfer，否则新 push 数据和 revise 值会被后续 rule 同拍读取，缓存依据也会改变。

一条 rule 本 tick 最多获准一次；重复检查和仲裁任务去重，未变化的条件不无故重试。一个 rule 等待多个 Queue 时，可能经历多次通知，不能保证每条依赖链只额外检查一次失败组件。

本方案不预先补齐整条潜在上游链，而是根据实际获准 pop 逐步通知相关等待者。它减少保守计算，但可能增加串行 delta 批次。遇到循环空间依赖，不会自动产生起点或解决停滞；具体竞争顺序、收敛和停滞处理仍需 review。

## 跨 tick 的缓存有效性

Tick 改变本身不使 proposal 失效。可否复用取决于实际计算依赖和操作目标是否仍然有效。

```text
R 读取 input 和 counter，算出 response
    → output 满，候选等待
    → 后续 tick output 腾出空间
    → input、counter 和消费目标都未变
    → 可复用 response，重新仲裁
```

若 Work 没有读取 output 的旧内容，纯粹的 output 空间变化不应让 payload 计算失效。资源 ready 可以变化，计算仍然有效。

需要检查：

- 本次实际读取的输入、内部状态和业务条件是否变化；若计算使用周期时间或其他外部值，也属于依赖。
- Pop 是否仍针对原来的输入元素。
- Revise 是否仍针对原来的元素或修改目标。
- 输入发生 pop 后又 push 相同内容，数值相同也不能视为原元素仍然存在。

可以使用版本或元素身份记录。初版用 Queue 粒度版本，覆盖相关读取和目标依赖，允许保守地多做重新计算；后续再考虑元素、字段或结构粒度。不要求为纯 append 的输出 push 引入无关的旧内容依赖。

缓存检查结果：

```text
有效 + 资源未就绪 → 继续等待
有效 + 资源就绪   → 重新仲裁
依赖或目标失效   → 废弃旧候选，重新 Work
```

初版也可以只复用同 tick 的候选，跨 tick 缓存作为后续优化；不能把“跨 tick 一律清理”理解为缓存的必然语义。

## Xfer 与下一 tick

Xfer 执行获准候选并清理对应操作。未获准但仍有效的候选可以保留；无效候选应清理。若采用跨 tick 缓存，不能沿用“清空所有 proposal”的统一处理。

本拍临时预约、accepted 列表和端口占用需要重置。Pending 候选与这些本拍管理记录分开维护。

全部提交完成后，依据读取依赖和操作目标变化检查、失效缓存，并安排相关任务。新 tick 的 push/pop 机会重置也需要通知等待者，即使 current 数据值或长度没有变化。只等待数据变化可能漏掉资源重试。

具体版本更新、通知和缓存检查顺序须保证：旧候选不会在新状态下未经验证就被 accept。

## 后续 Review

- 实际读取依赖和操作目标如何登记，覆盖条件读取和动态目标，避免缓存失效漏判。
- Queue 就绪查询、等待索引和最终预约保持一致；就绪不代替预约。
- 失效、重新 Work、成功提交时正确移除旧等待关系。
- Delta 去重、一次获准限制，以及仲裁状态重置带来的唤醒完整性。
- 所选 A/B 容量政策及 B 的拓扑序不被缓存改变；停滞和公平性另行确定。
- 正常完成、读取不足与缓存候选区分；部分 proposal 仍必须在仲裁收尾。
- 并行 Work、候选登记、通知收集和阶段屏障的线程安全。
- 测量 Work 次数、缓存复用与失效次数、等待检查次数、仲裁次数、delta 数量、内存及各阶段耗时。

本文保留优化方向，不规定最终容器、版本粒度、函数注册 ABI，也不要求当前实现所有缓存能力。
