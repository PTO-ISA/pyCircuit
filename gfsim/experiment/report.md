# GFSim 端到端实验报告

## 结论

当前单线程核心方案可以实现，调度核心为 428 行 Python。已运行的完整电路没有发现与独立参考模型不一致的结果：跨 tick 候选直接仲裁、读取失效、Work 屏障、同 tick 容量 DFS、原子确认、事件和 Xfer 可以协同工作。

这不是完整框架的验收结论：层级激活、外部驱动、事件取消等仍未定义；也没有证明任意电路均正确。测试采用 spec 的唯一 pop/push 来源前提，不评估端口竞争。

## 验证证据

14 个端到端测试入口（原合并的随机流水／存储测试按例子拆成两个，输入与覆盖保持不变），包含固定种子 0～5 的随机流水和存储请求、组件顺序反转、不同背压周期及反馈变体。所有请求通过真实 Module/Rule 处理；运行期间测试不修改候选或持久状态。1100 级满流水完整排空，访问栈超过 1000 层，未使用 Python 递归。

| spec 能力 | 完整电路中的触发与检查 |
| --- | --- |
| tick 0 全部激活、读空订阅、无同拍转发 | 空流水填充；精确核对首个输出 tick、后续每拍吞吐和最终休眠 |
| Module 选 Rule、Rule 选 proposal、未选中候选取消 | 包处理网络在输出背压期间切换 lane 和 bias；核对逐拍结果及全部有效订阅 |
| 必要读取失败与部分效果清理 | 双输入处理器先准备左输入效果，右输入延迟到达；输出和事件都不能提前发布 |
| 实际参数、动态下标和读取集合替换 | 系数表在线切换索引，同时更新曾经读过的旧表项；核对输出、版本、激活及固定读者表 |
| 缓存命中重新登记依赖 | 控制信号每拍变化，流水计算输入长期被背压保持；核对事件、读取关系及最终输出 |
| 跨 tick 保留并直接仲裁 | 周期性接收端解除流水背压；确认上游获准时 Module/Rule 计算次数均未增加 |
| 完整前驱访问、共享前驱、失败记忆 | 流水和原子双输出，初始 Work 集合随拍变化；固定点参考模型核对获准集合与提交 |
| Work 屏障先于容量仲裁 | 配置更新和接收端就绪出现在同拍，取消和替换必须先于提交；组件顺序反转后输出不变 |
| 全部参与 Queue 原子确认 | 两路原子输出共同被消费；持续背压不能部分提交，也不能提前发布事件 |
| 静态环与实际动态环 | 有空位反馈、退出分支、自身回收均完成；满环实际互相依赖时 runtime 和参考模型都报错 |
| revise→pop→push、元素身份 | 重试缓冲同 Rule revise/pop/push 相同值；存储 busy 的 audit 与 finish 分属不同 Rule；核对状态版本 |
| 无变化 revise 不通知 | 存储 audit 写入相同元数据、重复配置写相同值；逐拍对比事件和版本 |
| 纯事件、无效果不 firing、事件去重 | Source 等待和 Sink 定时就绪；空 Merge 正常完成但不获准；与状态通知合并时只 Work 一次 |
| 事件以获准 tick 为起点 | 双输入候选在输出背压中保留；每次获准后的事件必须是该 tick+3，清理候选不能删掉它 |
| Queue array 与稳定存储 | bank 表及系数表每个元素独立 QueueId；实际 deps、槽位与固定读者数组保持一致 |

独立参考路径不调用被测成员函数：各例子目录的 reference.py 给出组件事务，根目录的 reference.py 用固定点许可和函数式 Queue 提交。数字输出、包序号、重试次数、存储读回与最终内容另由 scoreboard 验证。测试比较集合而不固定互不依赖 Rule 的顺序。

为检查测试是否能识别关键错误，另在临时副本分别取消缓存订阅重登、把事件锚点改为 selected_tick、跳过原子许可检查、忽略读取代号匹配。四项修改均被现有端到端测试检出；修改没有写入仓库。

## 性能测量

2026-10-01，aarch64，Python 3.11.16；默认参数为 150 tick、16 级流水、每 bank 512 个表项、重计算循环 2000 次、重复 3 次取中位数。构造和首拍订阅不计时。完整原始结果见 [results.json](results.json)。

比较模式只关闭候选缓存，仍按相同事件和状态通知激活，不强制全量 Work。每组核对获准集合序列、最终全部 Queue 状态和剩余事件一致。测量使用完整电路的一段运行窗口；功能测试另检查有限输入全部完成。

| 电路 | 缓存开启 | 缓存关闭 | 关闭/开启 | 实际 Rule 计算：开启/关闭 |
| --- | ---: | ---: | ---: | ---: |
| 持续满流水 | 59.32 ms | 59.22 ms | 1.00 | 2700 / 2700 |
| 背压中的重计算 | 17.14 ms | 93.74 ms | 5.47 | 344 / 624 |
| 稀疏访问 bank 表 | 12.29 ms | 12.15 ms | 0.99 | 548 / 548 |

背压负载的 280 次缓存命中避免了重复业务计算；Module Work 次数均为 624，容量仲裁与结果相同。另一个完整流水测试确认容量传播可以直接提交旧候选，连 Work 入口都不需要再次进入。

bank 负载有 1034 个 Queue、6 个 Module、11 个 Rule，读者表共 6204 个槽位。若 C++ ReadGen 为 uint64，纯读者数据为 49,632 字节。运行窗口扫描 2916 个读者槽位，没有逐拍扫描全部 Queue。该负载没有缓存收益，开启缓存略有检查成本；这个幅度也会受计时噪声影响。

## 成本、缺口与适用限制

1. **固定读者表成本是实在的。**内存为 Q×M×sizeof(ReadGen)，通知为变化 Queue 数×M。1100 级满流水的 Module 数也很大，排空时需要大量扫描；完整测试约 80 秒，主要耗时来自这一场景。这不违反 spec，但不能把小 ModuleCount 的假设推广到很长的逐级 Module 链。
2. **deps 线性去重最坏为 O(d²)。**当前组件每 Rule 的实际依赖较少，用简单 vector 即可审阅；大量实际读取集中在一条 Rule 时，需要另测并决定辅助索引，实验没有声称这种负载高效。
3. **事件堆保存尚未到期的请求。**同 Module 同 tick 在到期时才去重，提前登记的重复事件仍占空间；代价取决于未到期事件数量。已发布事件取消／覆盖保持 Q06 未决。
4. **静态资源声明依赖编译器正确。**Queue array 的可能修改元素仍需构造来源槽位，动态 deps 只记录实际访问，二者不是同一成本。实验不校验所有潜在端口竞争。
5. **完整框架还有未决语义。**Q02/Q03/Q06/Q07/Q11/Q12 均没有通过实验被默认为已解决。外部输入由预装 ROM 的 Source 模拟；没有来源 0 协议、快照恢复或并行测试。Module 在已选中独立 Rule 后自身必要读取失败的分支，以及执行异常后的终止行为，尚未有独立端到端场景专门覆盖。

未发现需要擅自改变已确认调度语义才能通过这些电路的功能缺陷。Python 时间和对象内存均不能作为最终 C++ 性能结论；tuple 字段更新会重建小 aggregate，C++ 生成成员赋值可以直接修改目标。
