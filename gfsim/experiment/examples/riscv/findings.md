# CPU 实验发现与边界

本文件记录实现中遇到的具体限制。CPU 通过测试不代表前端／编译器或任意微架构已完成验证。

## F01. 有字段名的按值记录

- 问题：引擎最初只接受类型严格为 int、bool、tuple 的值，NamedTuple 会被拒绝。把五级流水写成大量数字下标会明显增加审阅成本。
- 处理：允许字段递归满足原值约束的 NamedTuple；比较保留具体记录类型，字段 revise 重建原记录类型。没有引入动态业务对象、可变 list 或 dict。
- 验证：流水数据贯穿 Fetched/Decoded/Executed/Completed，WB 对 Retired 的字段执行 revise；每拍检查实际记录类型，并比对退休值。核心小电路继续使用 tuple／标量值验证。
- 状态：已实现，是 Python 值表示的补充；对应 C++ 固定 struct。

## F02. 就绪判断的表达（已澄清，不属于调度缺陷）

- 触发：`lw x2,0(x0); add x3,x2,x1`，以及多周期 load 的相关指令。
- 澄清：pop 本来就只在整条 Rule 获准后的 Xfer 生效。stall／operands_ready 可以是控制输入或基于 current 计算的组合条件；条件不满足就不形成可执行候选。现有引擎已经支持，不应将此列为调度缺陷。
- 实现优化：移除原先的 Stall 异常。操作数选择显式返回 `(ready, value)`，阶段代码用普通 if 判断；本轮生成式成员函数直接调用 abort，清理部分 proposal 并保留订阅；正常路径直接 complete。错误路径丢弃 complete，执行条件未满足 abort。
- 边界：这是 runtime Work 的完成状态，不是仲裁批准，也不替前端定义业务返回值语法。没有给组合 stall 增加 Queue 或额外周期；已经由 Module 获得的控制条件也可以直接用于选择是否调用 Rule。

## F03. 延迟访存的开始和完成是两个事务

- 触发：sum.s 使用 `memory_latency=3/5`。
- 约束：input payload 读取形成消费需求；未获准候选的未来事件不会发布。因此不能读取请求、安排计时，同时暗中保留已消费的输入。
- 当前模型：开始事务真实消费请求并保存到 busy Queue，同时发布事件；完成事务再产生响应。busy 保存阶段间状态，事件只提供激活。开始事务没有容量相关输出，其 due 时间不会因背压错用候选计算 tick。
- 成本：增加一个请求保存槽位；busy 工作时 EX/MEM 可保存下一条指令。这是已声明的弹性结构，不能把它的时序当成整条流水同步冻结。
- 状态：现有引擎可以表达这种多周期单元。若要求保持输入 Queue 不动、另行启动依赖其 payload 的事务，需要重新讨论资源角色与事务边界；本例没有增加例外。

## F04. 前递值的生命周期不能省略

- 风险：前递源离开后，重新计算若使用较旧操作数，可能出错。直接让 EX 再读寄存器堆会增加读端口，不能隐去这项硬件成本。
- 当前模型：采用 ID 保存值、WB→ID 旁路、EX/MEM 和 MEM/WB 前递，以及 MEM busy 的未完成 load 检查；EX 没有额外的寄存器堆读取。
- 验证：长访存下穷举三条短窗口的 64 种 addi/load/store/nop 组合；另有最近 load 覆盖旧值、连续写同一寄存器、随机程序和模块顺序对照。未发现本模型的值丢失。
- 限制：此证据依赖单发射、顺序执行和当前缓冲／写回结构。增加 WB 背压、多发射或乱序后，必须重新验证操作数保持，不能自动套用结论。

## F05. 仿真失败后缺少禁止继续的保护

- 复现：既有反馈模型遇到实际容量环时第一次 step 报错，捕获后第二次 step 原先仍可推进。CPU 的非法指令和访存错误也暴露相同生命周期风险。
- 处理：Python Simulator 保存 failed 标记；step 内未处理的执行异常使实例失败，随后 step 明确拒绝。CPU 缺输入或操作数未就绪显式调用 abort 并返回，不会使实例失败。
- 验证：CPU 的非法编码、越界、未对齐和程序落出 ROM 场景，以及核心小电路容量环场景，均检查失败后不能继续。
- 状态：已修复；不承诺回滚已执行的部分仿真状态，也不提供精确 ISA 异常。

## 验证范围

本轮保留 14 个 CPU 测试并新增 36 配置的完整快照矩阵；核心和观察器测试见 [实验报告](../../report.md)。旧七组 Python examples 已移除，1100 级测试不属于此次验收。CPU 从汇编输入到退休与独立顺序解释器比对，并有流水拍数断言。

顺序解释器验证架构结果，不是第二个逐拍 CPU 微架构模型。所支持指令是 RV32I 子集，HALT 是教学环境约定；当前没有完整 ISA 合规验证、精确异常或多核内存模型验证。

## F06. 动态 dirty 位图没有让本轮 Python CPU 提速

- 实现：Module 管理实际 Rule 读者位图；队列变化与 var 参数变化设置同一 dirty 位。提交和 abort 保留读取，重算和取消清旧读取；缓存命中不扫描版本、不续订。
- 验证：36 配置与改造前逐拍 Queue、获准集合和未来事件完全一致。
- 观察：本轮三个 CPU 工作负载缓存命中均为零；新增位图读写、readSlots 清理和通知循环增加 Python 开销。测量整体慢约 17%～18%，不能将结构简化直接解释为运行加速。详细计时边界及原始样本见实验报告。

## F07. 固定槽位和自动读取登记的小步改进

- 改动：构造时保存 Queue.module_slots[mid]，读取直接定位；Queue 查询按 active_module/active_rule 自动登记，阶段中删除显式 record_read。消费仍由 pop 表达。
- 语义：读空也订阅；complete/abort 恢复 Module 读取上下文；Work 外观察不登记；pop/revise 独立保留目标依赖，重复登记位测试去重。读取集合及通知次数不变。
- 验证：37项测试通过，固定映射／自动登记两个中间版本的36组逐拍轨迹与本轮修改前一致，统计计数也一致。
- 测量：固定映射后耗时降低约1.9%，两项一起相对本轮修改前降低约2.3%；自动登记额外差值约0.5%，较小且可能受噪声影响，未消除 F06 的全部开销。增加了 QueueCount×ModuleCount 个槽位映射项。
- 说明：[读取登记报告](../../read-tracking.md)逐步解释当前实现，并保留三版本原始样本和源码校验值。
