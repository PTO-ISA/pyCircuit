# 开启 C 后 C++ 膨胀的原因

通用编译器修复及最终复测见[字段分析修复](field-analysis-2026-10-15.md)。以下数据保留为修复前诊断记录。

后续已完成 [Control 拆分对照实验](control-split-experiment.md)：保持所有七个输入，
只去掉 Control 聚合，就使 C 开启的头文件从 53,671 行降至 3,513 行、条件排序环从两个
变成零；六组各 64 拍的行为对照一致。以下保留拆分实验之前的诊断过程。

结论：主要膨胀发生在 C++ 后端的条件表达式生成。需求条件与共享边界形成额外的排序环，
触发整段表达式的递归回退；回退在分支之间不保留局部计算，反复展开同一 SSA 值。
C 解压增加表达式的规模和分支数量，放大了已有的问题。此次只诊断，未修改生产编译器或 CPU 模型。

## 实际触发条件

`CppLowering.cpp` 的 `CppStatements::value()` 先传播每个值的需求条件，随后同时沿
数据依赖和需求条件依赖排序。共享边界被布尔分析当作独立原子，并在调用共享计算前保留需求条件。
真实数据图无环，但加入这些条件边后不一定能整体排序。

两份输入均测到以下最小的循环结构，两条边都是需求条件边：

```text
共享条件 q ──需要先求需求条件──> Control.stall
Control.stall ──需要先求需求条件──> 共享条件 q
```

C 开启时，诊断编号为 `v745 -> v738 -> v745`；原始事务文件中的定义为：

```mlir
%592 = acir.extract %522 {field = "stall"} : (...) -> i1
%598 = arith.ori %592, %520 : i1
%599 = arith.andi %520, %598 : i1
```

这里 `q = A & (stall | A)`，布尔值上等于 `A`。但共享边界截断了布尔关系分析，
独立原子的需求分析仍引入 q 与 stall 互相依赖的边。这是后端添加的排序环，不是 CPU 电路的数据反馈环。
危险操作判定会沿操作数递归传播，涉及此类共享值的条件计算进入受保护的排序路径。

诊断消融：只向需求分析开放纯共享布尔操作的内部关系，第一个环消失，
但 Fetch 随后出现 `redirect` 的需求条件依赖自身的环，仍走同一回退。
因此只消除上述一个冗余布尔式或取消一次环检测，并不能解决问题。
这个消融版本仅为定位原因，未作为修复或完成语义验证的候选版本。

## 为什么一个排序环让整个 Fetch 膨胀

`CppLowering.cpp` 中检测到 `conditionalCycle` 后，当前整个 `value(root)` 调用退回递归 `emit()`。
危险的 select、布尔 and/or 生成 if/else。进入分支前保存 `available` / `computed`，
每条分支结束后恢复外层映射，以免引用离开作用域的局部变量。于是分支内计算无法被其他分支复用；
嵌套条件会重复生成同一组依赖。这个作用域处理有语义上的必要性，但当前回退缺乏其他复用机制。

单个 Fetch 根表达式的实际插桩计数：

| 项目 | C 关闭 | C 开启，同一程序字节 |
| --- | ---: | ---: |
| 不同的、进入递归生成的 SSA 值 | 161 | 634 |
| 递归生成次数，含常量 | 1,170 | 38,035 |
| 同一个 ROM read 的生成次数 | — | 1,354 |
| 同一个 ROM array.index 的生成次数 | — | 1,354 |

这是静态生成次数，不是每个 CPU 周期实际执行的次数，也不代表有 1,354 个不同的 ROM 端口。
产生的重复还包括索引、原始指令取数、比较和条件组合，不只包含 C 解压的计算。

此前同字节对照中，Fetch 方法从 2,698 行增长到 50,172 行；整个头文件的增加量
47,474 行全部来自 Fetch。事务 IR 从 2,332 个操作增至 3,031 个，RTL 友好 IR
从 30,710 个增至 31,397 个，说明主要代码尺寸放大发生在此 C++ 生成路径。

```sh

```

## 对应的前端结构

`model/model.py:309` 从当前流水寄存器和译码信号计算 load-use stall；315 行把它与
redirect、target、forwarding、ECALL wait、stop 打包为 `Control`；318–323 行让多个
独立 Rule 使用同一 control。Fetch 的 51 行用 `control.stall or control.ecall_stall`
决定保留当前级状态。前端没有写出 q；q 是事务提取生成的就绪条件组合。

另一个扩大保护范围的因素已经从事务文件核对：后端 `hazardous()` 沿所有操作数递归，
提取结构字段也会遍历整个 aggregate，未单独识别这个字段的实际依赖。因此查询 stall
时会追溯到 Control 的其他字段，经过 ExecutionResult 的 aggregate，最终到 ALU 的动态除法。
在当前文件中可沿 `%592 -> %522 -> %521 -> %513 -> %392 -> %390 -> %385 -> ... -> %181`
看到这条关系，`%181` 是 `arith.divui %99, %100`。这是后端的保守依赖分析，
不能理解为 load-use stall 在 ISA 语义上需要 ALU 除法结果。

“共享结构体 + 多个 Rule 消费 + 字段参与短路分支 + 条件执行的计算/资源就绪”是当前
已观察到的触发组合，不是每个要素的必要性证明，也未证明改写其中一个即可消除所有环。
特别是只开放共享布尔关系的实验已经显示另一个环；拆开 Control 也还不是经过验证的修复。
这类写法本身合法。前端应继续拒绝实际组合依赖环和不合法的跨事务值使用；本例所需的
编译器改进则是区分实际数据依赖、就绪/保护条件和保守的结构体依赖，并在无法全局排序时
保留条件执行及有界的计算复用。涉及 Signal/EHR 等有读取顺序语义的值，不能无条件提前或跨视图缓存。

证据目录：`pycircuit/builds/benchmarks/ripes5-standard/c-cause-20261015/`。
`manifest.json` 保存命令、输入和生产 lowerer 的 SHA256、头文件相同检查；
`c_off/diagnostic.log` 与 `c_on_same_bytes/diagnostic.log` 保存排序环、边类型和重复生成计数；
`summary.json` 汇总诊断计数及插桩脚本 SHA256。
`*-transparent-experiment/` 保存消融的结果，`transparent-experiment.json` 保存其构建参数。

后续修复应保留短路、断言和资源读取语义，处理需求条件的排序以及回退时的复用。
不能直接删除环检测，也不能把受条件保护的除法、数组索引等全部提前计算。
