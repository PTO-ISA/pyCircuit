# RV32IMC 与 Ripes5 对照审查

> 以下保留最初审查的结论和证据。四项发现现均已修复；当前结果见[修复验证](fixes-2026-10-15.md)及[缺陷清单](../tests/known-issues.json)。

本次审查结论：**尚不能认定实现已完成验收。** 已保存的用例有可复核的通过证据，但发现了 CPU 边界错误、输入加载错误和比较器漏检。此前将“当前用例通过”表述成“实现完成”过于肯定。

本轮保留当前 CPU、编译器、原生 runner 和原有结果，另建反例与复测目录；没有修改上述实现来使反例通过。基线文件 SHA256 保存在 [baseline.json](audit/baseline.json)。

## 已复现的问题

| 优先级 | 问题 | 复现结果 | 影响 |
| --- | --- | --- | --- |
| P1 | 错误路径取指立即报越界 | 从 PC=4092 的合法 JAL 跳回 PC=0。原生 RV5S 运行 12 拍、退出 42；模型在第 2 拍取顺序后继 4096 时断言失败，来不及冲刷。生成 C++ 也报错。 | 合法程序会错误终止；Fetch 边界错误需要像非法编码一样保留到确定执行路径后再处理。 |
| P1 | ELF 加载器漏掉已分配的段 | `.extra` 位于合法 RAM 地址 0x1000，内容是整数 42。加载器只复制 `.text` 和 `.data`，把该数据变成零。模型、原生和顺序预期全部退出 0，而原 ELF 程序应返回 42。 | 三方一致仍可建立在共同错误输入上。当前顺序预期独立于 CPU decode，但不独立于 ELF 输入转换。 |
| P2 | store 宽度没有独立比较 | 把旧程序两次 SW 事件的 size 从 4 改为 1，不改其他轨迹。`compare_native()` 仍通过。 | 当前比较器不能支撑“所有访存事件字段严格一致”的表述。它用模型提供的宽度掩码参考数据，没有独立检查参考写宽度。 |
| P2 | store 后立即打印字符串存在新参考差异 | 初始 a7=4、a0=0x1000，先将字符 A 写入 RAM，紧接 ECALL。顺序预期和模型输出 A，原生输出空字符串；流水状态比较仍相同。 | 原生回调在 store 提交前读取字符串，而模型观察器在本拍提交后恢复输出。原有测试没有覆盖这一时序组合；完整 `run()` 的最终输出检查会发现该差异。不能自动将其加入允许差异清单。 |

源码位置：

- [Fetch.advance](../model/model.py:56)：在取指时直接断言，没有让错误路径访问等待冲刷。
- [compile_program](../tests/program.py:88)：只抽取 `.text`／`.data`；后面检查了其他段的地址范围，却没有装载其内容，也没有验证固定段起始地址。额外只读段还可能使 `.text` 不从零开始，而输入仍把它放在零。
- [compare_native](../tests/e2e.py:59)：store 掩码使用模型的事件 size；不像 load 那样比较参考侧尺寸。
- [原生回调](../tests/native/runner.cpp:136) 与 [model_output](../tests/e2e.py:108)：字符串读取时刻不同。

具体程序、原生 JSONL、模型 IR／C++ 和结果见 [probes.json](audit/probes.json)。复现脚本为 [probes.py](../tests/audit/probes.py)。这些是审查发现，尚未修复。

## 原有通过证据的复核

重新读取并核对了完整常规验收的 62 个程序，共 6049 拍：

1. 输入 JSON 的 SHA256 与记录一致；生成 ACPy 包装器里的文本、RAM、寄存器与输入一致。
2. 原生初态与同一输入一致；事务 IR、RTL 友好 IR、生成 C++ 的保存轨迹逐项相同。
3. 重新运行当前比较器、顺序预期校验；61 个程序在比较器当前检查的字段上相同，`upstream_rvc` 仅出现已记录的 6 项差异。
4. 检查这些已有 ELF，已分配的非空段均为 `.text`、`.data`、`.bss`；`.text` 地址为 0，`.data` 地址为 0x1000。**本轮 ELF 反例没有证明这 62 个既有输入已经装错**，它证明加载器的通用正确性不足。
5. 另从当前原生二进制重新采集 `load_branch_wrong_path`、`m_extremes`、`upstream_rvc`，与保存的模型轨迹复核一致（rvc 保留原有差异）。
6. Ripes／VSRTL 工作树干净，固定 commit 与此前来源记录相符；当前 runner 与 adapter 的 SHA256 也与构建来源记录一致。

逐程序审查结果见 [corpus-review.json](audit/corpus-review.json)。已有 76 项回归通过日志是真实的通过记录，但这些新反例说明测试覆盖不充分。

“75 个指令名称执行过”是覆盖统计，不能等同于完整 ISA 一致性证明；原生差异的已有“3 个缺陷／2 个不支持”也是当时所测程序的分类，不是穷尽清单。

## 性能 benchmark 是否成立

原计时区间没有发现明显错误：

- C++ 和原生都在构造后预热 1000 拍，再计时 100000 次真实 tick／clock。
- 计时内关闭轨迹；原生同时关闭界面端口通知、clock 通知和反向历史。
- 打印最终快照在计时之后；未把编译、进程启动、JSON 输出计入运行时间。
- 原生窗口内退休 75000 条，持续执行循环；不是测到退出后的空转。C++ 与原生的最终 PC、全部寄存器、全部 RAM 和退休数相同。

本轮将进程固定到同一可用 CPU 核，并以“原生先／C++先”交替顺序串行运行，每种配置 5 次。使用既有 `-O3` 二进制，并记录了二进制 SHA256：

| 配置 | 生成 C++，拍／秒 | 原生 RV5S，拍／秒 | C++ / 原生 |
| --- | ---: | ---: | ---: |
| IM、32 位机器码 | 375716 | 141297 | 2.66 倍 |
| IMC、16／32 位混合机器码 | 36177 | 139905 | 0.259 倍 |
| 与第一行完全相同的 32 位机器码，但两边都启用 C | 92260 | 143172 | 0.644 倍 |

原来的约 37 万／3.6 万拍每秒和对原生的相对结果基本复现，因此该混合循环的性能差异有实测依据。

需要收窄此前解释：

- 原来的 IM 与 IMC 是同一汇编逻辑的两种机器码，不是只改变一个 C 配置开关。不能把约十倍差异全部归因于开启配置。
- 相同机器码的新控制组仍显示启用 C 后约四倍的额外开销；这证明当前生成模型存在明显实现开销，但没有 profiling，不能断言根因已定位到哪一个 helper／编译 pass。
- 只有一个带乘除、load-use、固定 taken 分支的热循环；尚不能据此给所有算法、所有 Ripes5 工作负载或 IR 解释器下总体速度结论。
- 两个模型的内存表示、诊断和观察逻辑不同。这是本应用模型的实测对照，不能直接视为纯编译器优化能力的比较。

见 [benchmark-review.json](audit/benchmark-review.json) 及 [复测脚本](../tests/audit/benchmark_review.py)。

## 当前应采用的状态

**当前用例集有有效的对照证据；通用实现和验证链仍有已复现的问题，尚未完成最终验收。**

后续讨论应先处理错误路径取指、ELF 输入装载和比较器漏检，并明确 ECALL 字符串观察时序。性能优化应建立在修正后的验证链上。
