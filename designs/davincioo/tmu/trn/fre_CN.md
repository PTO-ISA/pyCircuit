# TMU.TRN.FRE — 空闲列表

- 源候选项：`DAV-TMU-TRN-FRE-0001`
- 硬件层次：**H3**，位于 H1 `TMU` / H2 `TRN`
- NDF 细化：**L2 微架构**；模块级 L1 行为链接仍需评审。
- 建议处置：**叶节点**（提议，尚未获目录批准）
- 拟定实现路径（若接受为独立叶节点）：`designs/davincioo/tmu/trn/fre.py`
- 当前设计计划执行状态：**代码已实现，还没跑 gfsim 验证**。有一条验收条件做不到，
  是框架限制，写在"未决决策"里。

FRE 管物理 tile 空间的分配：哪块空着、这个版本占了哪块、什么时候能收回。

## 它解决什么问题

一条 Tile 指令写的是逻辑名，比如"写 tile 3"，但数据最终得落在 BANK 的某一片物理存储上。
谁来决定这次写放到哪片、以及哪些片还没被占用？这就是 FRE。

它管一张账：一个 PE 有多少块物理 tile 空间，哪些占着，哪些空着。谁要写一个新版本，先来
问 FRE 要一块；这个版本彻底不要了、而且确认没人还在读它，再还给 FRE。

还有一层。核是推测执行的，分支可能猜错，所以"要一块空间"不能是一次性的动作，得能撤销。
FRE 因此把分配拆成两步：先预留，之后再提交或取消。猜错时取消，空间原样还回来，就像从来
没申请过。

## 在系统里的位置

一个 Tile 的生命周期被切给了好几个模块，各管一段。FRE 只管"物理空间归谁"这一段：

| 谁 | 管什么 | 不管什么 |
| --- | --- | --- |
| [RAT](rat.md) | 逻辑名到版本号的映射 | 这个版本的数据在哪 |
| **FRE** | **哪块物理空间空着、这个版本占了哪块** | **空间里装了什么、这个版本有没有被写过** |
| [STS](sts.md) | 版本的描述符、写没写过、发布没发布 | 数据字节 |
| [BANK](../trf/bank.md) | 数据字节本身 | 这块空间归谁、什么时候能回收 |
| [REF](../trf/ref.md) | 还有几个人正在读这个版本 | 有没有权限真的回收 |
| [LTR](ltr.md) | 把上面几家的动作串成一个有序事务 | 任何一份状态 |

所以 FRE 既不知道数据内容，也不知道一个版本"有没有意义"，它只知道"这块空间被占了"。
反过来，别人也无权决定空间的归属——分配这件事只有 FRE 一个所有者，
[alc.md](../trf/alc.md) 记录了看起来像分配的那个候选项为什么并入这里。

## 一次操作怎么走完

四种操作都从同一条请求流进来，靠 `operation` 字段区分。

**分配。** 请求带一个事务号 `txn_key`。FRE 先按这个号查一遍：如果这个事务之前已经要过
空间，就把上次给的槽号再报一遍，不会给第二块。重命名可能因为流水线重放而重复发来，这一步
保证重放不会白占空间。没查到就找一个空槽，同时占一行预留表，两件事在同一个 tick 一起生效。
这时空间是"预留"状态，还能撤销。

这里有个地方要留神：重复的分配请求，`slot_index` 给的是它已经拿到的那个槽、`matched` 会置上，
但 `accepted` 是 **false**——因为 `accepted` 表示的是"账本有没有改变"，而重复请求什么都没改。
调用方必须看 `matched` 才能把"你已经有这个槽了"和 `exhausted`（真的失败）区分开。只看
`accepted` 会把一次成功的重放误判成拒绝。

**提交。** 分支确认走对了，这个版本要真的活下来。FRE 把预留行撤掉。此后这块空间只能靠
"释放"收回，取消不再起作用。

**取消。** 分支猜错了，或者这条指令被冲掉了。FRE 把预留行撤掉，同时把槽标回空闲。查预留行
的条件里带了"这行还活着"，所以提交之后再来取消会什么都查不到、什么都不改——重复取消是安全的。

**释放。** 这个版本彻底不要了。但 FRE 自己判断不了能不能释放：它看不到还有几个人在读（那是
REF 的账），也看不到逻辑上是不是已经没人引用（那是 RAT 那边的事）。所以请求必须把这两个结论
带上，FRE 只负责检查两个都为真，然后按 owner 和版本号找到那个槽，标回空闲。

每种操作的应答从各自的端口出去。查询是第五条路，只读，不掺在上面四种里。

## 输入

| 名称 | 载荷/类型 | 含义 | 证据状态 |
| --- | --- | --- | --- |
| request | AllocRequest | 一次分配、提交、取消或释放。看 `operation` 区分是哪种，用 `txn_key` 认事务 | 已实现 |
| query | CapacityQuery | 问一下池里还有没有空槽，不改任何状态 | 已实现 |

## 输出

| 名称 | 载荷/类型 | 含义 | 证据状态 |
| --- | --- | --- | --- |
| alloc_ack | AllocRequest | 分配结果。`slot_index` 是拿到的槽号；`accepted` 表示账本有没有变，所以重复的事务会是 `matched` 置上而 `accepted` 为 false；`exhausted` 说池是不是满了 | 已实现 |
| commit_reservation_ack | AllocRequest | 预留已转正。这个版本现在是活的，只有释放才能收回它 | 已实现 |
| cancel_reservation_ack | AllocRequest | 预留已撤销，槽已归还 | 已实现 |
| free_version_ack | AllocRequest | 槽已释放；两个前提缺一个就拒绝 | 已实现 |
| answered | CapacityQuery | 查询结果，`has_free_slot` | 已实现 |

提议表格中的载荷名称在字段、位宽和名义身份冻结前均为设计伪类型。Queue 传输由编译器推断，不应要求公开的 Queue 包装器。时钟/复位/时间域属于执行上下文，不得臆造为普通载荷端口。

## 所有或包含的状态

- 一个槽池，`TILE_SLOTS_PER_POOL` 项，一项一个物理 tile 槽，只有一处会写它。Local 每个 PE
  一份，Shared 每个 core 一份
- 每个槽存：owner、TileVersion、分配代际、以及一个"已分配"位
- 一张预留表，`RESERVATION_SLOTS` 行，以 `txn_key` 为键，只装还能取消的在途预留
- 不存任何数据字节，不存描述符，不存逻辑名，也不管生命周期

## 参考实现

[`fre.py`](fre.py) 定义变更规则 `serve_allocation`、只读规则 `answer_capacity_query`，
以及系统 `trn_fre_system`。类型和冻结的常量通过
[`contracts/tmu_trn.py`](../../contracts/tmu_trn.py) 共享。

上面四种操作靠四次查表定位。查重那次要求预留行还活着且 `txn_key` 对得上。找空槽和找空预留行
是分配同时需要的两样资源，两个都有才动手，两次写挂在同一个条件下——这就是"分配要么全成要么
全不成"的实现方式。找目标槽那次按 owner 和版本号找，因为释放请求就是这么来的：回收链传的是
版本号，从来不是槽号。

一条 rule 服务全部四种操作，这就是分配器单端口的原因：一条 rule 每 tick 只收一个 token，
所以每周期最多一次操作打到池上。每个数组只有一处会写，这是 Decision 0151 的要求。查询由另一
条 rule 处理，它读同一个池但从不写，所以查到的是真实状态，也不用排在变更操作后面等。

## 与卡片原设想的差异

有三处和这张卡片最初的提议不一样。前两处是框架逼的，第三处是架构判断。

**四种操作合成一条流，而不是四个请求端口。** 一条 rule 要等它的每个输入都来了 token 才触发
（Decision 0167/0168），而分配、提交、取消、释放是各自独立到达的，做成四个端口就会互相干等，
卡死。合成一条流其实也更接近真实硬件——分配器只有一个端口，一个周期本来就只处理一次操作。
应答仍然按 `operation` 用一个普通 route 分回各自端口。

**Local 和 Shared 用同一套槽几何，而且 Shared 是独立的一份实例。** 槽号字段的位宽刚好够装
本池的槽数，而框架没有位宽转换原语，所以两个容量不同的池没法共用一套请求记录。Shared 也不能
塞进按 PE 展开的实例里：它是 core 级的，四个按 PE 展开的 rule 去写同一个 Shared 池，就等于给
一个表开四个写端点，Decision 0151 不允许。`scope` 字段是给父层用的，父层靠它决定送到哪个实例，
FRE 自己不读——这跟 BANK 不读 `cell_key` 是一个道理：按某个字段分流的人，必须是唯一解释它的人。

**物理资源是一组固定数量、固定大小的槽，不是一片可任意切分的堆。** 卡片原文说的是"extent"
（范围），听着像可变长度。但 TRF 是 Tile **寄存器文件**，硬件本来就是固定槽结构，跟物理寄存器
池一样。这个判断同时也被框架印证：要分配一段变长区间，就得在表里找连续的若干项，而框架既没有
归约算子也没有找连续段的原语；找一个固定大小的空槽只要一次 `ac.find`。槽的几何参数是从 BANK
和 BGF 的契约导进来算的，这样一个池刚好覆盖一个 PE 的全部 cell，两边不会各说一套。

## 已冻结的决策

卡片原先把分配策略、物理容量、复位镜像构造列为未决。实现时定成了这样：

| 决策 | 取值 | 理由 |
| --- | --- | --- |
| 分配单位 | 一个固定大小的槽 | 变长区间需要找连续段，框架没有这个原语 |
| 池容量 | `TILE_SLOTS_PER_POOL = 64` | 查空槽的逻辑不依赖具体槽数，改这个值不用改代码 |
| 单槽大小 | 算出来的：`CELLS_PER_PE / TILE_SLOTS_PER_POOL` | 从 BANK/BGF 导入，保证一个池刚好覆盖一个 PE 的 cell |
| 复位镜像 | 全零；槽里存 `allocated` 而不是 `free` | Decision 0151 只支持全零初始化，这样存就不需要复位 FSM |
| 预留表容量 | `RESERVATION_SLOTS = 32` | 它限制的是同时在途的重命名事务数，不是活跃版本数——行在提交时就撤了 |
| 容量答案 | 一个 bool，不是数字 | 框架没有归约算子，见"未决决策" |

## 后端边界

持久索引变量在 Decision 0151 里算临时状态，PYC/RTL 必须明确拒绝，所以目前只有 gfsim 能跑
这个模块。[bank.md](../trf/bank.md) 记了同一条边界，以及要怎么改框架才能去掉它。

## 需验证的能力

- 参数化的分 bank 位图/数组状态 —— **能做**，池就是一个元素为扁平 struct 的持久索引变量
  （Decision 0151）
- 有界的范围选择 —— **对"一个固定大小的槽"能做**，`ac.find` 带 `where`/`key` 就能挑出一个
  空项。但**挑不出连续的若干项**，这就是分配单位定为一个槽的原因
- 关联的幂等表 —— **能做**，按 `txn_key` 查重，重复的事务返回它已经拿到的槽
- 原子地"预留 + 应答 + 取消/释放" —— **能做**，两次写挂在同一条件下一起生效，而且四次查表
  可以在一条 rule 里共存
- 非零复位初始化 FSM 或已验证原语 —— **不需要**。槽里存 `allocated` 而不是 `free`，全零就
  表示"每个槽都空着"
- PYC/RTL 的表降级 —— 只要存储还算临时状态，就**按设计被拒绝**，见"后端边界"

这些是待验证的要求，并不证明当前框架缺少相应能力。先测试当前修订版；确认缺口后，将其作为通用框架/原语问题加入回归，并先合入共享修复，再提交依赖设计的 PR。

## 行为验收

- 分配要么全成要么全不成 —— **做到了**。写槽和写预留行由同一个条件把着，所以不可能出现
  "槽占了但没有预留行"的状态
- 重复的 RenameTxnKey 返回同一个预留 —— **做到了**。查重在任何分配动作之前完成，报出去的是
  查到的那个槽，不是新分配的
- 某个 PE 耗尽不会占用别的 PE 的池 —— **结构上就成立**。池是在 system 内部声明的，每份实例
  各有一个，没有任何端口把池暴露出去
- 释放同时要求逻辑许可和 REF 计数为零 —— **做到了**。两位都跟着请求来，都会被检查；而且找
  目标槽时还要求那个槽已分配、owner 和版本号都对得上
- 物理容量耗尽要用反压处理，不能臆造架构故障 —— **没做到**，见第一条未决决策。FRE 没有臆造
  任何故障，也没丢请求：它照样应答，带上 `exhausted` 和 `accepted=False`。但它把请求吃掉了，
  没有留住，所以反压退化成了重试

设计局部证据：`designs/davincioo/tests/fabric/test_fre_slot_allocator.py`。

gfsim 执行是首个实现门槛。PYC/RTL 义务适用于获准的降级结果；拒绝临时存储的部分仍须明确后续工作。仅编译证据不能证明行为正确。

## 未决决策

- **池满时没办法让请求方等着，这条验收做不到。** Decision 0210 规定 rule 吃不吃输入这件事
  必须由一个恒真的条件决定，而且明确说了：不输出的那条路径**照样会把输入吃掉**。所以"池满了"
  这种从状态算出来的条件，没法把请求留在队列里。现在只能总是应答、带上 `exhausted`，请求不丢
  但要重试。要真正解决，得让框架支持"消费与否由状态决定"，这是通用能力，该在上游做。这跟 REF
  遇到的是**同一个缺口**，不是新的一个。测试里固定了现在的行为，等这个能力落地，那条断言就会
  失败，提醒回来改。
- **容量查询只能答"有没有"，答不了"还剩几个"。** 框架没有归约算子，所以数不出空槽的个数，
  `has_free_slot` 只能说存不存在。[alc.md](../trf/alc.md) 把容量投影并进了这个接口，而这就是
  FRE 实际能答出来的部分。真要一个数字，要么框架提供归约能力，要么调用方自己记账。
- **槽号的位宽只能写字面量，不能由容量算出来。** 前端要求 `ac.bits[...]` 里是静态宽度
  （`ACPY-TYPE-003`），因为它把注解当源码文本解析，看不到常量的值，所以 `SLOT_INDEX_BITS`
  没法用来定字段宽度。现在靠一条断言锁住字面量和池容量一致，但改容量得同时改两处。
- **Shared 池挂在谁下面还没定。** 它不能待在按 PE 展开的实例里，否则一个表就有四个写端点，
  所以它是同一个 system 的另一份实例。但真正持有它的父层到底是 TRN 组装还是 core 级组装，
  没有记录。
- **分配代际带着走，但从不参与比较。** 它存在槽里、释放时回显一下，所以回绕的代际暂时还不会
  让一次过期的释放误伤别人。要不要让它参与目标槽的匹配，这个还没定。
