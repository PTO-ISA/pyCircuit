# TMU.TRN.STS — Tile 状态

- 源候选项：`DAV-TMU-TRN-STS-0001`
- 硬件层次：**H3**，位于 H1 `TMU` / H2 `TRN`
- NDF 细化：**L2 微架构**；模块级 L1 行为链接仍需评审。
- 建议处置：**叶节点**（提议，尚未获目录批准）
- 拟定实现路径（若接受为独立叶节点）：`designs/davincioo/tmu/trn/sts.py`
- 当前设计计划执行状态：**代码已实现，还没跑 gfsim 验证**。有一条验收条件做不到，
  是框架限制，写在"未决决策"里。

STS 回答"这个版本到底是什么"：描述符是什么、真正被写进去了多少、出过什么错、有没有变成
架构状态。

## 它解决什么问题

[FRE](fre.md) 给出一块物理空间，[RAT](rat.md) 让一个名字指向某个版本，但这两家都不知道
版本本身的任何事。它是什么形状？元素是什么类型？里面写过东西没有，还是分配完就一直是垃圾？
产生它的过程中出过错没有？它对架构上更晚的指令可见了，还是仍然是推测的？这些归 STS。

其中最要紧的区分是**分配**和**已定义**。拿到存储只是说"这块地方允许被写"，完全不代表写过。
一个消费者去读一个分配了但从没写过的版本，读到的是这块空间上一次留下的内容。所以 STS 存
两张互相独立的覆盖掩码——分配掩码和初始化掩码——只有第二张盖住了第一张，这个版本才算定义完整。

## 在系统里的位置

一个 Tile 的生命周期被切给了好几个模块。STS 只管"这个版本是什么、可不可见"这一段：

| 谁 | 管什么 | 不管什么 |
| --- | --- | --- |
| [RAT](rat.md) | 逻辑名到版本的映射 | 版本本身的任何属性 |
| [FRE](fre.md) | 这个版本占了哪块物理空间 | 那块空间有没有被写过 |
| **STS** | **描述符、覆盖情况、第一个错误、发布状态** | **数据字节、名字、物理块** |
| [BANK](../trf/bank.md) | 数据字节本身 | 这些字节有没有意义 |
| [REF](../trf/ref.md) | 还有几个人正在读这个版本 | 它是不是架构状态 |

"发布"这个词故意在两个地方出现，含义并不一样。RAT 发布的是**名字**：从现在起这个名字指的是
这个版本。STS 发布的是**版本**：这个版本的内容和描述符定稿了。协调者两件都要做，单做一件
都是不完整的。

## 一次操作怎么走完

四种会改状态的操作都从同一条请求流进来，靠 `operation` 区分。查询走自己那条只读流。

**预留（reserve）。** 出现了一个新的推测版本。STS 找一行空的，把描述符和这个版本被允许覆盖
的分配掩码填进去。初始化掩码显式写成 0：这个版本有了存储，但没有内容。如果这一行已经存在，
预留会被拒绝，所以同一个版本不会被描述两遍。

**写入（write）。** 生产者写了这个版本的一部分。写是分成好几次局部更新到达的，所以覆盖是
**合并**而不是替换——一次替换式的更新会把之前所有写过的覆盖抹掉。同一个操作也带着描述符。
错误码保留的是**第一个**：行里已经有错误就保持不变，所以调用方读到的是引发后续问题的那个错，
而不是最后报上来的那个。写入受分配代际限定，已发布的行拒绝写入。

**发布（publish）。** 版本变成架构状态。这是唯一一个"先校验再改"的操作：请求里的描述符要和
已提交的那一行比对，不兼容就带着 `rejected` 拒绝，所有字段原封不动。不存在"不兼容的版本先
可见、之后再纠正"的窗口，因为兼容性检查是那次写的条件的一部分，不是事后的补救。

**回退（rollback）。** 推测猜错了，把这个推测行撤掉。能够到的只有同一个分配代际的推测行：
已发布的行和更新的代际都碰不到，这正是陈旧的恢复抹不掉架构状态的原因。

**查询（query）。** 一条只读通路，报出描述符、两张掩码、保留的错误码，以及这个版本是推测的
还是已发布的。`contents_defined` 是用两张掩码算出来的，不是存下来的，所以它和掩码不可能打架。

每种回执从各自的端口出去，所以某个预留的消费方堵住了，不会连带把发布也卡住。

## 输入

| 名称 | 载荷/类型 | 含义 | 证据状态 |
| --- | --- | --- | --- |
| request | StatusRequest | 一次 reserve/write/publish/rollback，靠 `operation` 区分、用 `allocation_generation` 限定 | 已实现 |
| query | StatusQuery | 读一个版本的状态快照；不改任何状态 | 已实现 |

## 输出

| 名称 | 载荷/类型 | 含义 | 证据状态 |
| --- | --- | --- | --- |
| status_reserve_ack | StatusRequest | 推测行已建立；`exhausted` 表示表满 | 已实现 |
| status_write_ack | StatusRequest | 覆盖已合并、描述符已更新；`fault_code` 是保留下来的第一个错误 | 已实现 |
| status_publish_ack | StatusRequest | 版本已成为架构状态；描述符不兼容则 `rejected` | 已实现 |
| status_rollback_ack | StatusRequest | 推测行已删除；行已发布或代际不符则拒绝 | 已实现 |
| answered | StatusQuery | 描述符、两张掩码、保留的错误码，以及 `contents_defined` | 已实现 |

提议表格中的载荷名称在字段、位宽和名义身份冻结前均为设计伪类型。Queue 传输由编译器推断，不应要求公开的 Queue 包装器。时钟/复位/时间域属于执行上下文，不得臆造为普通载荷端口。

## 所有或包含的状态

- 一张 `STATUS_ROWS` 行的状态表，按 `(owner, tile_version)` 定位，只有一个写者，声明在
  系统内部，所以每个重命名作用域各有一张
- 每行存：owner、版本、分配代际、dtype、layout、shape、有效区域、分配掩码、初始化掩码、
  保留的错误码、speculative、published、live
- 不存数据字节、不存逻辑名、不存物理块号、不存引用计数

## 参考实现

[`sts.py`](sts.py) 定义会改状态的规则 `serve_status_request`、只读规则
`answer_status_query`，以及系统 `trn_sts_system`。类型和冻结常量放在
[`contracts/tmu_trn.py`](../../contracts/tmu_trn.py) 里共享。

行是按 `(owner, tile_version)` **搜索**出来的，不是索引出来的，因为版本号是稀疏的：16 位的
空间里同时活着的只有有限几个。这和 RAT 的映射表正好相反——那里逻辑名是稠密下标。两种形状
就是这两个模块用不同原语读自己状态的原因。

一条规则服务全部四种操作，这也正是"状态表是单端口"的含义：一条规则一个 tick 只吃一个 token。
表恰好一个写者，这是 Decision 0151 的要求。查询是第二条规则，读同一张表，所以它看到的是
真实状态而不是缓存快照，也不会排在某次修改后面。

降级出来的模块里，write、publish、rollback 三次行写被合并了——它们写的都是搜索到的那一行，
而且三种操作互斥；预留保留了自己那次写，因为它写的是一行空行。

## 与卡片原设想的差异

**四种会改状态的操作共用一条流，而不是四个请求端口。** 一条规则只有在**每个**输入都有 token
时才会 fire（Decision 0167/0168），而 reserve、write、publish、rollback 是各自独立到达的，
四个端口会互相等成死锁。回执仍然从各自端口出去，靠一个按 `operation` 分流的 route。四种操作
正好填满两位分支，所以不像 RAT 和 CHK 那样需要一个拒绝端口。

**元素定义度是一张 64 位掩码，不是通用表示。** 卡片把"有界的定义度表示"留为未决。掩码是载荷
类型族里最宽的值，而且没有归约算子，所以"这个版本定义了多少"只能靠比较两张掩码来回答，算不出
数量。需要更细粒度的版本需要的是另一种表示，而不是更宽的字段。

**描述符字段是不透明的标量。** `dtype`、`layout`、`shape`、`valid_region` 都是定宽值，STS
只做相等比较，从不解释它们。所以兼容性就是精确相等，不是子类型或布局规则。如果某个配置需要
"兼容但不相同"的描述符，得先把这个判定说清楚，STS 自己没有描述符语义。

**发布是单目的地的。** 卡片要求 Shared 的多目的地发布不能暴露新旧混合的记录。一次规则激活写
一行，所以跨多个目的地的发布是多次操作，这个叶节点没法让它们原子化；见"未决决策"。

**每种操作都通过同一次"选中索引 + 选中值"的写完成。** 同一份状态上的两次写必须可证不相交或
可证互斥，而分析器从彼此独立的操作条件里推不出这两点，第二次写会被
`same-owner proposals may select one index concurrently` 拒绝。所以索引和值都是选出来的，
互斥变成了结构性的。
**只读查询规则会卡住 C++ 生成，所以这个所有者暂时还没有 gfsim 证据。** 规则验证器接受这份
设计、`acir-opt` 也能冻结它，但 `acir-queue-cxxgen` 会以 `table firing contract is
unsupported` 拒绝整个模块。原因不在查询本身：一个只**预留**表的 firing——只读规则读写者那张表
就会降级成这个形状——没有主写，而生成器要求每个带状态的 firing 都指名一个主写。最小复现是一个
十六行的系统：一张表、一条写规则、一条读规则；把读规则删掉就能生成。
`compiler/acir/lib/CodeGen/QueueGraphGenerator.cpp` 里有三处都假设存在主写，所以这是框架能力
缺口，该由上游解决，不该在设计里绕过去。[chk.md](chk.md) 能生成，正因为它没有查询规则。

## 已冻结的决策

| 决策 | 取值 | 理由 |
| --- | --- | --- |
| 表容量 | `STATUS_ROWS = 64` | 行是搜出来的，所以这是个参数，不是写死在逻辑里的假设 |
| 行的键 | `(owner, tile_version)` | 版本稀疏，所以行是找出来的而不是索引出来的 |
| 覆盖 | 两张 64 位掩码：分配与初始化 | 分配不能蕴含已定义，一张掩码表达不了两件事 |
| 定义度 | 由掩码算出，从不存储 | 存一份就是给掩码已经承载的事实找了第二个所有者 |
| 错误保留 | 第一个错误优先；`FAULT_NONE = 0` | 0 表示"无错误"，于是复位镜像和新建的行不用初始化过程就一致 |
| 复位镜像 | 全零；行里存 `live` | Decision 0151 只允许全零镜像 |
| 兼容性 | dtype/layout/shape 精确相等 | STS 没有可以用来推理的描述符语义 |

## 后端边界

持久索引变量在 Decision 0151 下属于临时状态，PYC/RTL 必须在一个明确的边界上拒绝它，所以
gfsim 是唯一能执行这个叶节点的后端。[bank.md](../trf/bank.md) 记录了同一条边界，以及要消掉
它需要做的框架工作。

## 需验证的能力

- 支持部分字段/掩码更新的关联 Table —— **可用**；`ac.find` 定位行，不可变字段更新写它的一部分
- 跨 Queue/Table 的原子事件 —— **可用**；行写和回执在一次被推断出来的事务里一起提交
- 有界的元素定义度表示 —— **以 64 位掩码的形式可用**；见"与卡片原设想的差异"
- 多个独立反压的输出 —— **可用**；route 给每种回执各自的端口和容量
- 层次化 PYC/RTL Table 降级 —— **按设计拒绝**，只要存储还是临时状态；见"后端边界"

这些是待验证的要求，并不证明当前框架缺少相应能力。先测试当前修订版；确认缺口后，将其作为通用框架/原语问题加入回归，并先合入共享修复，再提交依赖设计的 PR。

## 行为验收

- 分配不蕴含数据已定义 —— **成立**；两张掩码是分开的字段，预留写入的是零初始化掩码，所以
  这条性质是状态本身而不是约定
- 回执被堵住时不得消费请求、也不得写入 —— **对输出反压成立**；被推断出来的事务在任何效果
  发布之前就把选中的输出预留下来了，所以回执队列满时表完全不动。但表满时**不成立**；
  见第一条未决决策
- 发布在改变可见状态之前先校验描述符兼容性 —— **成立**；兼容性是那次写的条件的一部分，不兼容
  的发布报 `rejected` 且所有字段原封不动
- 回退不能抹掉更新的已发布代际 —— **成立**；条件要求是同一分配代际、且未发布的推测行
- Shared 多目的地发布不能暴露新旧混合的记录 —— **没有解决**；这里的发布一次一行。多目的地
  发布究竟是一次事务还是一个有序协议，未决
- STS 不含数据字节 —— **成立**；行里只声明了描述符、覆盖和状态字段，设计本地测试直接盯着
  声明来断言

设计本地证据：`designs/davincioo/tests/fabric/test_sts_status_table.py`。

gfsim 执行是首个实现门槛。PYC/RTL 义务适用于获准的降级结果；拒绝临时存储的部分仍须明确后续工作。仅编译证据不能证明行为正确。

## 未决决策

- **表满的时候没法把请求方阻塞住。** Decision 0210 把规则的消费条件固定成一个"可证恒真"的
  候选条件，并且明确假分支**可以**消费输入，所以一个从表占用率推出来的条件留不住队列里的请求。
  找不到空行的 reserve 只能带着 `exhausted` 回答。这和 FRE、REF、RAT 记录的是同一个缺口，
  要补上需要框架层面的"状态限定消费"。
- **多目的地发布没有事务。** 一次激活写一行，所以要让多个目的地原子发布，要么这份存储支持
  掩码式多行更新，要么用一个"先暂存再提交"的协议。架构想要哪一种没有记录，在定下来之前这条
  验收就没法满足。
- **描述符兼容性等同于相等。** 发布是否可以合法地收窄或重新解释描述符，尚未确定；如果可以，
  那个判定必须写清楚，STS 推不出来。
- **描述符快照形式仍是一组标量。** 卡片要的是快照或句柄形式。四个不透明标量就是那组快照；
  是不是该换成指向描述符存储的句柄，取决于真实描述符有多大，而这个数在整个设计计划里还没有
  任何地方记录。
- **覆盖粒度没有说明。** 一张 64 位掩码盖 64 个单位，但一个单位到底是一个元素、一个 cell
  还是一行，没有冻结。[bank.md](../trf/bank.md) 定死了物理 cell 大小，所以两者的对应关系
  必须先说清楚，掩码才有精确含义。
