# TMU.TRN.CHK — 检查点

- 源候选项：`DAV-TMU-TRN-CHK-0001`
- 硬件层次：**H3**，位于 H1 `TMU` / H2 `TRN`
- 建议处置：**叶节点**（提议，尚未获目录批准）。这张卡片原本写的是**待评审**，因为归属在
  独立叶节点和 RAT 私有状态之间没有定论；理由见"为什么它是一个叶节点"。
- NDF 细化：**L2 微架构**；模块级 L1 行为链接仍需评审。
- 拟定实现路径（若接受为独立叶节点）：`designs/davincioo/tmu/trn/chk.py`
- 当前设计计划执行状态：**已通过 gfsim 验证**。下面的行为验收是以真实事务跑在生成模型上的，
  见"后端边界"。有一条验收按设计归别人管、另有一条做不到，都写在"未决决策"里。

CHK 记住"该退回到哪里"。一个检查点就是一个数字——某个值得回到的时刻，[RAT](rat.md) 的
历史栈有多深。

## 它解决什么问题

核是推测执行的，所以必须能把重命名状态退回到更早的某个点。[RAT](rat.md) 其实已经把需要的
东西都留着了：每一个被顶掉的映射都躺在它的历史栈上，一次回退弹一条。RAT 唯一没留的是
**该在哪停**。

一条可能被预测错的分支，会在自己前面存一个检查点。如果预测错了，恢复就把 RAT 的历史退到
那个检查点记下的深度。所以一个检查点的全部内容就是一个 frontier——一个栈深——加上标识它的
身份。

这就是这个设计最核心的省法：CHK 存的是一个数字，不是映射表的副本。把被顶掉的映射复制到这里，
等于给 RAT 已经拥有的事实找了第二个所有者，而且会让恢复深度被 CHK 的容量卡住，而不是被 RAT
的历史深度卡住。

## 为什么它是一个叶节点

这张卡片原本的未决问题是：检查点机制该做成一个模块，还是做成 RAT 的私有状态。结论是叶节点，
理由只有一条：这两份状态回答的是不同的问题，生命周期也不一样。RAT 的历史是"每个被顶掉的映射
一条"，被撤销它的那次回退消费掉。检查点是"每个推测点一个"，能活过很多次 swap，并且在分支正确
解决时被释放——而分支预测对了才是常态，那种情况下根本不会发生任何回退。

把两者合并会把它们塞进同一条规则，于是一次 capture 和一次 swap 会为同一个单端口所有者争用，
尽管它们根本不共享状态。分开的代价是一条连接面，换来的是每个所有者只干一件事。

做成叶节点**没有**换来的东西是驱动恢复的能力。CHK 从不写 RAT、FRE、STS；它回答一个 frontier
和一段距离，回退动作本身是 RAT 的事务，而 RAT 会拿自己的栈顶再校验一遍。所以一次恢复被两个
所有者各限定了一次，谁也不信谁。

## 在系统里的位置

| 谁 | 管什么 | 不管什么 |
| --- | --- | --- |
| [RAT](rat.md) | 映射表，以及能撤销它的历史栈 | 一次恢复该在哪停 |
| **CHK** | **存下来的 frontier，以及它们还能不能用** | **映射表、历史栈，以及恢复的逐步推进** |
| [FRE](fre.md) | 物理空间和可撤销的预留 | 任何重命名状态 |
| [STS](sts.md) | 版本描述符和发布状态 | 任何重命名状态 |

## 一次操作怎么走完

三种操作都从同一条请求流进来，靠 `operation` 区分。

**捕获（capture）。** 请求方刚从 RAT 拿到一次 swap 回执，所以它知道当前的历史深度。它把这个
深度连同一个检查点身份发过来，CHK 把这一对存下。同一个身份重复捕获，返回的是它已经有的那条
记录，不会再占第二行，所以被重放的捕获不会漏掉检查点容量。

**回退（unwind）。** 推测猜错了。CHK 查出这个检查点，回答两件事：该退回到哪个 frontier，
以及需要多少次回退才能到——也就是请求方当前深度和记录深度之间的距离。记录保持存活，所以
一次因反压中断的恢复可以重来；把记录撤掉会让第二次尝试看起来像是在用一个不存在的检查点。

当记录的 frontier **比**当前的更深时，这次回退被标成 `stale` 拒绝。这一次比较就是全部的
陈旧性规则，值得说明它为什么够用：一个在恢复目标点之后才捕获的检查点，其 frontier 必然更深，
所以恢复一旦完成，它就永远过不了这个检查。不需要任何人去扫表把恢复刚刚作废掉的那些检查点
标记出来。

**释放（release）。** 分支解决对了，这条记录还回去。之所以要有它，是因为池子是有界的，而
预测正确是常态；没有释放，一个从不预测错的程序照样会把池子占满。

每种回执从各自的端口出去。第四个端口收的是不在封闭集合里的操作，在那里被拒绝。

## 所有或包含的状态

- 一个 `CHECKPOINT_SLOTS` 条记录的检查点池，只有一个写者，声明在系统内部，所以每个重命名
  作用域各有一个
- 每条记录存：flow key、检查点身份、捕获时的 frontier、live
- 不存映射行、不存历史记录、不存回退游标，不存任何兄弟模块的状态

## 参考实现

[`chk.py`](chk.py) 定义规则 `serve_checkpoint_request` 和系统 `trn_chk_system`。类型和冻结
常量放在 [`contracts/tmu_trn.py`](../../contracts/tmu_trn.py) 里共享。

两次搜索定位工作：这次请求指名的那条记录，以及给新捕获用的一行空位。一条规则服务全部三种
操作，这让池子保持单端口、写者保持唯一，正是 Decision 0151 的要求。

回退什么都不写。这一点在降级出来的模块里是看得见的：只有两个写条件——capture 和 release——
而且都不是 unwind 的条件，`test_an_unwind_reports_a_distance_rather_than_driving_it` 盯的
就是这条。这是"不直接修改兄弟模块状态"这条验收能拿到的最强形式：根本没有兄弟状态可改，因为
它们够都够不着。

## 与卡片原设想的差异

**CHK 不拥有回退相位。** 卡片把"若为独立叶节点则含历史 frontier 与回退相位"列为所有状态。
frontier 归这里，相位不归——而且这是框架限制，不是偏好。

每周期吐一个回退步骤，需要一个既能**由请求触发登记**、又能**没有请求也推进游标**的所有者。
一条规则要么由 token 触发、要么由状态触发，不能两者兼有。拆成两条规则——一条登记、一条排空——
会让游标有两个写者，Decision 0151 不允许；单独那条排空规则本身是可以写出来的，但它没法知道
有新的回退开始了，除非去读兄弟规则写的状态然后再把它清掉，那还是同一个"两个写者"问题，只是
绕了一层。

所以恢复由调用方驱动：CHK 说退多远，RAT 每次回退弹一条。正确性上什么都没丢——RAT 的栈仍然
保证从新到旧、每一步仍然校验代际——但这个时序推进在这个叶节点里不是一个硬件状态机，需要它的
配置得先等框架能力。

**陈旧性是推出来的，不是扫出来的。** 要把一次恢复作废掉的那些检查点标记出来，需要掩码式的
多行更新，而这份存储没有：一次搜索只写一行。frontier 比较让这次扫描变得没必要，这个结果其实
比扫描更好，但值得记一笔：另一条路本来就走不通。

**多了一个 release 操作。** 卡片只列了 capture 和 unwind。一个有界的池子如果没有归还的途径，
在预测正确这条常态路径上就会被占满，所以 release 不是额外功能，而是这套机制能成立的前提。

**多出一个端口，接不在封闭集合里的操作。** 三种操作填不满两位分支，而 route 的选择子落在
`[0, outputs)` 之外是确定性的运行时失败，所以畸形请求在一个端口上被拒绝，而不是让模型失败。

## 已冻结的决策

| 决策 | 取值 | 理由 |
| --- | --- | --- |
| 处置 | 叶节点 | 检查点和历史回答不同的问题、生命周期也不同；见"为什么它是一个叶节点" |
| 检查点内容 | 一个 frontier 加身份 | RAT 已经留着被顶掉的映射，复制一份等于制造第二个所有者 |
| 池容量 | `CHECKPOINT_SLOTS = 16` | 约束并发的推测点数量；行是搜出来的，所以这是个参数 |
| frontier 来源 | 随请求带进来 | CHK 不观察 RAT；读兄弟模块状态的模块就成了那份状态的第二个所有者 |
| 陈旧性 | `current_frontier >= frontier` | 恢复目标点之后捕获的检查点 frontier 更深，所以一次比较替掉一次扫表 |
| 复位镜像 | 全零；记录里存 `live` | Decision 0151 只允许全零镜像 |

## 后端边界

持久索引变量在 Decision 0151 下属于临时状态，PYC/RTL 必须在一个明确的边界上拒绝它，所以
gfsim 是唯一能执行这个叶节点的后端。[bank.md](../trf/bank.md) 记录了同一条边界，以及要消掉
它需要做的框架工作。

CHK 确实走到了这个后端。`ac.jit(trn_chk_system).lower_acir()` 经 `acir-opt` 和
`acir-queue-cxxgen` 降级成检查点池上的一个类型化 `gfsim::QueueTableTransition`，设计本地的
gfsim 测试会编译并运行它。这两个工具用 `dev-llvm22` preset 从 `compiler/acir` 构建；工具或
C++20 编译器缺席时，测试是 skip 而不是 fail。

它的兄弟模块还走不到这一步，原因不在它们的存储：[rat.md](rat.md) 和 [sts.md](sts.md) 记录了
"只读查询规则"这个缺口——凡是在写规则旁边还带一条查询规则的所有者，C++ 生成都会被卡住。
CHK 能生成，恰恰因为它没有查询规则。

## 需验证的能力

- 有界的 Table/栈语义 —— **可用**；池子是一份持久索引变量，它需要的顺序性在 RAT 的栈里，
  不在这儿
- 多周期、带确认的恢复事务 —— **不可用**；一条规则要么由 token 触发要么由状态触发，所以
  逐步推进不归这里管。见"与卡片原设想的差异"
- 经父级 Queue 与 RAT/FRE/STS 原子协调 —— **可用**；这里的回答是本叶节点自己状态上的一次
  事务，它描述的那次恢复是一串 RAT 事务
- PYC/RTL Table 降级 —— **按设计拒绝**，只要存储还是临时状态；见"后端边界"

这些是待验证的要求，并不证明当前框架缺少相应能力。先测试当前修订版；确认缺口后，将其作为通用框架/原语问题加入回归，并先合入共享修复，再提交依赖设计的 PR。

## 行为验收

- 恢复从新到旧展开 —— **成立，但归 RAT 所有**；CHK 报出目标和距离，RAT 每次回退弹自己的栈顶，
  所以顺序是 RAT 那份存储的形状。CHK 违反不了它，也不负责保证它
- 陈旧的检查点不能恢复更新的映射 —— **成立，而且是两道**：CHK 拒绝 frontier 比当前更深的
  回退，RAT 又独立拒绝栈顶代际对不上的回退
- 不直接修改兄弟 RAT/FRE/STS 的状态 —— **结构上成立**；这个模块只声明一份所有者、只消费
  一条请求流，兄弟状态根本够不着

设计本地证据：`designs/davincioo/tests/fabric/test_chk_checkpoint_stack.py` 在降级出的
模块上断言结构；`designs/davincioo/tests/fabric/test_chk_gfsim.py` 把上面这些验收真的跑在
gfsim 里：一次捕获、一次重复捕获、一次回退的距离、一次陈旧回退、一次释放、一个未知操作，
以及池满。

gfsim 执行是首个实现门槛。PYC/RTL 义务适用于获准的降级结果；拒绝临时存储的部分仍须明确后续工作。仅编译证据不能证明行为正确。

## 未决决策

- **回退相位没有所有者。** 一个每周期吐一步回退的硬件时序器，需要一条既由请求触发、又由自身
  状态触发的规则，而框架给不出这种规则，除非让一个游标有两个写者。在这个能力出现之前，恢复的
  逐步推进归调用方。这是真实的能力缺口，不是设计上的取舍。
- **池满的时候没法把请求方阻塞住。** Decision 0210 把规则的消费条件固定成一个"可证恒真"的
  候选条件，所以找不到空位的 capture 只能带着 `exhausted` 回答，而不是被留住。这和 FRE、REF、
  RAT、STS 记录的是同一个缺口。
- **检查点身份由谁分配没有所有者。** `checkpoint_id` 和 `flow_key` 是随请求进来、被比较的，
  从不由这里生成。谁保证身份唯一、以及一个身份在记录还活着时被复用会怎样，尚未确定。
- **frontier 是被信任的。** `current_frontier` 来自请求方，而请求方是从 RAT 的回执里读到的。
  请求方要是错了，距离就是错的。CHK 不观察 RAT 就检查不了它，而观察就等于成为 RAT 深度的第二个
  所有者，所以这份信任是刻意的，但应该写进父层的契约里。
- **和 FRE 预留的关系没有说明。** 一次把映射退回去的恢复，同时必须取消那些 swap 占下的预留。
  这里没有任何东西负责把两者排序，该负责的协调者是 [LTR](ltr.md)，而它还没实现。
