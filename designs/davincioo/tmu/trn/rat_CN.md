# TMU.TRN.RAT — 寄存器别名表

- 源候选项：`DAV-TMU-TRN-RAT-0001`
- 硬件层次：**H3**，位于 H1 `TMU` / H2 `TRN`
- NDF 细化：**L2 微架构**；模块级 L1 行为链接仍需评审。
- 建议处置：**叶节点**（提议，尚未获目录批准）
- 拟定实现路径（若接受为独立叶节点）：`designs/davincioo/tmu/trn/rat.py`
- 当前设计计划执行状态：**代码已实现，还没跑 gfsim 验证**。有一条验收条件做不到，
  是框架限制，写在"未决决策"里。

RAT 只回答一件事：一个逻辑 tile 名字现在指的是哪个物理版本，以及这个名字哪个版本
是架构上算数的。

## 它解决什么问题

一条 Tile 指令写的是"读 tile 3、写 tile 5"，这些数字是逻辑名。核是推测执行的，所以
tile 5 可能被好几条还没确定下来的指令先后写过，每一次写都是一个独立的物理版本。总得有
个地方说清楚：这个名字现在指哪个版本；万一推测被丢掉，哪个版本才是真的。这就是 RAT。

它管一张表：每个逻辑名当前指向的版本，以及这个名字最后一个变成架构状态的版本。重命名
读这张表找源操作数，再给目的操作数装上一个新版本。

还有一层，恢复能不能做全靠它。装新版本会把上一个版本的记录覆盖掉，所以在覆盖之前，RAT
先把要被顶掉的那一行压进一个历史栈。回退就是把栈顶弹出来、原样放回去。没有这个栈，猜错的
分支就没法撤销；有了它，撤销无非就是弹栈。

## 在系统里的位置

一个 Tile 的生命周期被切给了好几个模块。RAT 只管"名字指谁"这一段：

| 谁 | 管什么 | 不管什么 |
| --- | --- | --- |
| **RAT** | **逻辑名到版本的映射，以及能把它撤销的历史栈** | **这个版本的数据在哪、里面装了什么** |
| [FRE](fre.md) | 哪块物理空间空着、这个版本占了哪块 | 名字指的是谁 |
| [STS](sts.md) | 版本的描述符、写没写过、发布没发布 | 哪个名字能找到它 |
| [CHK](chk.md) | 存下来的恢复点（指向 RAT 的历史深度） | 表本身；它从不写 RAT |
| [BANK](../trf/bank.md) | 数据字节本身 | 上面任何一项 |

[LRM](lrm.md) 不是第五个所有者。它是 RAT 的 Local 投影的名字，处置明确写着是别名：一个
Local 请求就是 `scope = SCOPE_LOCAL` 的 `MapRequest`，由每个 PE 各自那份实例来回答。
不存在第二张表。

## 一次操作怎么走完

三种会改状态的操作都从同一条请求流进来，靠 `operation` 区分。查询走自己那条只读流。

**换名（swap）。** 重命名要给一个逻辑名装上新版本。RAT 先读出这个名字当前那一行，把新版本
写进去，再把旧的那一行压进历史栈。两次写受同一个条件控制，所以绝不会出现"映射被覆盖了、
但能恢复它的记录没留下"。回执里报的是被顶掉的那个版本号，以及新的栈深——这个栈深正是
[CHK](chk.md) 拿去当检查点存的东西。

**发布（publish）。** 产生这个版本的指令退休了，于是它变成架构状态。RAT 把这一行标成已发布，
并记下这是最后一个发布的版本。请求带着 `map_generation`，只有和表里那行对得上才执行，所以
一个跑输给新 swap 的 publish 不会顺手把更新的版本给发布了。

**回退（rollback）。** 推测猜错了。RAT 弹出最新的一条历史记录，把它保存的那一行完整还原：
版本号、代际、最后发布的版本，以及这个名字当时到底有没有值。最后这点很关键——一个在 swap
之前根本没有版本的名字，必须回到"没有版本"，而不是回到版本 0。请求带着它要撤销的那个代际，
只有和栈顶对得上才执行，所以陈旧的恢复撤不掉它没见过的工作。

因为历史是个栈，连续回退天然从新到旧，全程不需要比较年龄。顺序就是存储的形状本身。

**查询（lookup）。** 一条只读通路，报出某个名字当前的版本、最后发布的版本，以及当前这个是不是
架构状态。不允许读推测状态的消费者在这里就能判断，不必再去问 STS。

每种回执从各自的端口出去。第四个端口收的是不在封闭集合里的操作，在那里被拒绝。

## 输入

| 名称 | 载荷/类型 | 含义 | 证据状态 |
| --- | --- | --- | --- |
| request | MapRequest | 一次 swap/publish/rollback，靠 `operation` 区分、用 `map_generation` 限定 | 已实现 |
| lookup | RenameLookup | 读一个名字当前的映射；不改任何状态 | 已实现 |

## 输出

| 名称 | 载荷/类型 | 含义 | 证据状态 |
| --- | --- | --- | --- |
| map_swap_ack | MapRequest | 新映射已装上。`reported_version` 是被顶掉的版本，`history_depth` 是新的栈深，`history_full` 表示这次 swap 被拒 | 已实现 |
| map_publish_ack | MapRequest | 版本已成为架构状态；代际对不上则拒绝 | 已实现 |
| map_rollback_ack | MapRequest | 旧映射已还原。`logical_id` 报的是被还原的那个名字，因为回退本身并不挑名字 | 已实现 |
| refused | MapRequest | 不在封闭集合里的操作，给出回答而不是让选择子越界 | 已实现 |
| answered | RenameLookup | 当前版本、最后发布的版本，以及当前这个是否已发布 | 已实现 |

提议表格中的载荷名称在字段、位宽和名义身份冻结前均为设计伪类型。Queue 传输由编译器推断，不应要求公开的 Queue 包装器。时钟/复位/时间域属于执行上下文，不得臆造为普通载荷端口。

## 所有或包含的状态

- 一张 `LOGICAL_TILE_REGS` 行的映射表，一个逻辑名一行，只有一个写者。Local 每个 PE
  一份，Shared 每个 core 一份
- 每行存：当前版本、映射代际、最后发布的版本、valid、published
- 一个 `MAP_HISTORY_DEPTH` 深的历史栈，存被顶掉的行，外加一个标量栈深
- 不存数据字节、不存描述符、不存物理块号、不存检查点

## 参考实现

[`rat.py`](rat.py) 定义会改状态的规则 `serve_map_request`、只读规则
`answer_rename_lookup`，以及系统 `trn_rat_system`。类型和冻结常量放在
[`contracts/tmu_trn.py`](../../contracts/tmu_trn.py) 里共享。

两份存储的形状是刻意做得不一样的。映射表按逻辑名**直接索引**，因为名字本身就是下标：
命名空间是稠密的，复位之后每个名字都存在。历史是个**栈**，因为回退必须从新到旧，而
`ac.find` 的 key 选的是**最小值**，年龄这件事根本没法表达成一次搜索。

一条规则服务全部三种操作，这也正是"映射表是单端口"的含义：一条规则一个 tick 只吃一个 token。
每份状态都恰好一个写者，这是 Decision 0151 的要求。查询是第二条规则，读同一张表，所以它
不会排在某次修改后面。

降级出来的模块里，swap 和 publish 对映射行的两次写被编译器合并了——它们写的是同一个下标，
而且两种操作互斥。合并之后必须仍然成立的性质是那个配对关系：压栈那次写的条件，恰好是合并
条件里 swap 那一半，`test_a_swap_installs_and_records_together` 就是盯这条。

## 与卡片原设想的差异

**三种会改状态的操作共用一条流，而不是三个请求端口。** 一条规则只有在**每个**输入都有
token 时才会 fire（Decision 0167/0168），而 swap、publish、rollback 是各自独立到达的，
三个端口会互相等成死锁。共用一条流也更贴近硬件：单端口的映射表一个周期本来就只服务一次操作。
回执仍然从各自端口出去，靠一个按 `operation` 分流的 route。

**复位镜像是全零，所以复位后的名字是"还没有版本"，而不是指向某个版本。** 卡片原本要求
一个非零的架构复位镜像。Decision 0151 只允许全零镜像，所以行里存的是 `valid`，复位后的名字
读出来就是"还没有版本"。如果某个配置需要复位即恒等映射——名字 *i* 指向版本 *i*——那用镜像
是表达不出来的，得有非零镜像能力或者一个显式初始化过程，这两样现在都没有。FRE 存 `allocated`
而不是 `free` 是同一类处理。

**多出一个端口，接不在封闭集合里的操作。** 三种操作填不满两位的分支，而 route 的选择子
落在 `[0, outputs)` 之外是确定性的运行时失败。所以畸形请求得到的是一个端口加一次拒绝，
而不是让整个模型失败——一条请求流绝不能产出"没有回答"。

**Local 和 Shared 是同一个系统的两次实例化。** Shared 不能塞进每个 PE 的实例里：它是 core
拥有的，四个 per-PE 规则去写同一张 Shared 表就等于四个写端点，Decision 0151 不允许。`scope`
是带给父层选实例用的，RAT 自己从不读它——理由和 BANK 从不读 `cell_key` 一样。

**每种操作都通过同一次"选中索引 + 选中值"的写完成。** 同一份状态上的两次写必须可证不相交或
可证互斥，而分析器从彼此独立的操作条件里推不出这两点，第二次写会被
`same-owner proposals may select one index concurrently` 拒绝。所以索引和值都是选出来的，
互斥变成了结构性的。
**只读查询规则会卡住 C++ 生成，所以这个所有者暂时还没有 gfsim 证据。** 规则验证器接受这份
设计、`acir-opt` 也能冻结它，但 `acir-queue-cxxgen` 会以 `table firing contract is
unsupported` 拒绝整个模块。原因不在查询本身：一个只**预留**表的 firing——只读规则读写者那张表
就会降级成这个形状——没有主写，而生成器要求每个带状态的 firing 都指名一个主写。最小复现是一个
十六行的系统：一张表、一条写规则、一条读规则；把读规则删掉就能生成。
`compiler/acir/lib/CodeGen/QueueGraphGenerator.cpp` 里有三处都假设存在主写，所以这是框架能力
缺口，该由上游解决，不该在设计里绕过去。[chk.md](chk.md) 能生成，正因为它没有查询规则。

## 已冻结的决策

卡片原本把命名空间大小、复位映射、推测历史深度、Shared 命名空间编码都列为未决。实现冻结了
其中三项：

| 决策 | 取值 | 理由 |
| --- | --- | --- |
| 逻辑命名空间 | `LOGICAL_TILE_REGS = 64` | 名字就是下标，所以命名空间大小就是表的形状 |
| 名字位宽 | `ac.u6`，与命名空间等宽 | 超出命名空间的名字是不可表示的，而不是回绕到某个活着的映射上 |
| 历史深度 | `MAP_HISTORY_DEPTH = 32` | 它约束的是推测深度，不是活着的版本数：一条记录要么被 rollback 弹掉，要么被 publish 解决掉 |
| 复位镜像 | 全零；行里存 `valid` | Decision 0151 只允许全零镜像 |
| 历史顺序 | 栈 + 一个标量深度 | `ac.find` 选最小 key，"从新到旧"表达不成搜索 |

Shared 的 `namespace_scope` 编码仍未决；`scope` 只是被带着走、由父层路由，这里从不解释它。

## 后端边界

持久索引变量在 Decision 0151 下属于临时（provisional）状态，PYC/RTL 必须在一个明确的边界上
拒绝它，所以 gfsim 是唯一能执行这个叶节点的后端。[bank.md](../trf/bank.md) 记录了同一条边界，
以及要消掉它需要做的框架工作。

## 需验证的能力

- 多维参数化映射存储 —— **一维可用**；映射表是一份持久索引变量。Local/PE 的投影是实例几何，
  不是第二个维度
- 关联式推测历史 Table —— **可用，但刻意不做成关联式**；历史是栈，因为"从新到旧"不是搜索
- 映射/历史的原子更新与多条响应通路 —— **可用**；两次写在同一个条件下提交，响应经 route 扇出
- 非零架构复位镜像 —— **不可用**；见"与卡片原设想的差异"
- PYC/RTL 状态降级 —— **按设计拒绝**，只要存储还是临时状态；见"后端边界"

这些是待验证的要求，并不证明当前框架缺少相应能力。先测试当前修订版；确认缺口后，将其作为通用框架/原语问题加入回归，并先合入共享修复，再提交依赖设计的 PR。

## 行为验收

- 四条 PE 流即使逻辑 ID 相同也互不干扰 —— **结构上成立**；映射表声明在系统内部，每份实例
  各有一张，没有任何端口把它暴露出去
- Shared 只有一个映射所有者 —— **成立**；Shared 是一次实例化、一条写规则，而不是一张被四个
  per-PE 规则写的 core 级表
- 重复的 RenameTxnKey 返回此前的回执 —— **部分成立**；这里的幂等性靠的是代际限定而不是事务号。
  重复的 publish 或 rollback 只要代际对不上就被拒绝、什么都不改，安全性质是有的。但重复的
  **swap** 会装上第二个版本，因为 RAT 没有预留行可以认出它——`txn_key` 的幂等归 [FRE](fre.md)
  管，同时握着两边的协调者不能对一个已经拿到回执的 swap 再发一次
- 历史满时要在 FRE 分配落定之前先阻塞 —— **做不到**；见第一条未决决策。RAT 会带着
  `history_full` 拒绝这次 swap 并且完全不动栈，所以没有任何东西被弄坏、这次 swap 可以重试，
  但请求是被消费掉了而不是被留住
- 回退只还原代际匹配的历史，并且从新到旧 —— **成立**；栈顶必须和 `map_generation` 对得上，
  而弹栈本身就是从新到旧

设计本地证据：`designs/davincioo/tests/fabric/test_rat_alias_table.py`。

gfsim 执行是首个实现门槛。PYC/RTL 义务适用于获准的降级结果；拒绝临时存储的部分仍须明确后续工作。仅编译证据不能证明行为正确。

## 未决决策

- **历史满的时候没法把请求方阻塞住，所以那条验收做不到。** Decision 0210 把规则的消费条件
  固定成一个"可证恒真"的候选条件，并且明确假分支**可以**消费输入，所以一个从栈深推出来的
  条件留不住队列里的请求。RAT 因此总是给出回答，带上 `history_full`。什么都没丢，但反压退化
  成了重试。这和 FRE、REF 撞上的是同一个缺口，不是第三个；要补上需要框架层面的"状态限定消费"，
  那属于上游能力。设计本地测试把当前行为钉住了，能力落地之后那条断言会失败。
- **复位映射做不成恒等映射。** 只有全零镜像，所以"复位后名字 *i* 指向版本 *i*"表达不出来。
  架构到底要不要这个、还是"还没有版本"才是正确的复位语义，得先定下来才能算缺口。
- **swap 的幂等性在 RAT 内部没有所有者。** `txn_key` 随请求带着走但从不比较，因为认出重复
  需要一行预留记录，而那行在 FRE 里。RAT 该不该自己留一行事务记录，还是由协调者保证至多一次
  投递，尚未确定。
- **名字位宽是字面量，不是推导出来的表达式。** 前端把注解当源文本解析，要求那里是静态位宽，
  所以 `LOGICAL_INDEX_BITS` 没法用来给字段定宽。一条断言保证字面量和命名空间不脱节，但改
  命名空间要改两处。
- **Shared 那份实例的宿主还没定**，理由和 FRE 的 Shared 池一样：父层到底是 TRN 组装还是
  core 级组装，没有记录。
