# TMU.BGF.MAP — 映射器

- 源候选项：`DAV-TMU-BGF-MAP-0001`
- 硬件层次：**H3**，位于 H1 `TMU` / H2 `BGF`
- NDF 细化：**L2 微架构**；模块级 L1 行为链接仍需评审。
- 建议处置：**叶节点**（提议，尚未获目录批准）
- 拟定实现路径（若接受为独立叶节点）：`designs/davincioo/tmu/bgf/map.py`
- 当前设计计划执行状态：**代码已实现，还没跑 gfsim 验证**。这一级是 BGF 的入口解码，请求在
  哪排队、bank 里存什么，都不归 MAP 管。

MAP 把客户端给的 `cell_key` 算成一对物理坐标 `(bank, row)`，指明是哪个 cell，请求的其他部分
一概不动。

## 它解决什么问题

客户端——CUBE、VEC 或 TLSU——要访问一个 cell，手里只有一个 `cell_key`。它不知道、也不该知道
数据落在哪个 bank 的哪一行。把这个名字换成一个地址的，就是 MAP。

MAP 是 BGF 的入口，也是这个决策唯一的所有者：BGF 里没有别的模块重算 bank 或 row。正因如此，
bank 的几何参数可以只在 BGF 内部知道——改几何只动 MAP 和共享契约，碰不到 CUBE、VEC、TLSU。

## 在系统里的位置

BGF 内部的路是固定的：客户端 → MAP 解出位置 → [RQ](rq.md)/[WQ](wq.md) 按类别排队 →
[ARB](arb.md) 扇出到 bank 并解冲突 → [XBAR](xbar.md) → [BANK](../trf/bank.md) 真正读写
字节。MAP 是第一环：

| 谁 | 管什么 | 不管什么 |
| --- | --- | --- |
| **MAP** | **把 `cell_key` 解成 `(bank, row)`** | **排队、仲裁，也不碰数据** |
| [RQ](rq.md) / [WQ](wq.md) | 读写队列，每个源类别一条 | 不看数据内容，不做任何决策，也不带 bank 维度 |
| [ARB](arb.md) | bank crossbar、冲突裁决、公平性与老化 | 一个 cell 在哪，它只读 MAP 写好的结果 |
| [XBAR](xbar.md) | 把已接受的授权送到目标 bank | 谁赢了这件事 |
| [BANK](../trf/bank.md) | 数据字节本身 | 这些字节归谁、谁有权访问 |

所以 `bank` 只有一个地方写、一个地方读。[rq.md](rq.md) 和 [wq.md](wq.md) 只是把记录带着走，
不看里面的内容，而 [arb.md](arb.md) 用 `bank` 挑冲突树。这就是为什么 `bank` 是数据里的一个
字段，而不是队列的一个维度：它得穿过中间排队那一段，才能到达唯一用它的人。

TRN/TRF 那一侧，一个 Tile 的其余生命周期各有各的主：[FRE](../trn/fre.md) 定一个版本占哪块
物理空间，[REF](../trf/ref.md) 数还有几个人在读，[STS](../trn/sts.md) 管描述符和发布状态。
这些 MAP 一概不问。它只回答关于 `cell_key` 的一道算术题，别的什么都不做。

## 一次解码怎么走完

进来的是六条客户端 lane，一条对应一个 `(source_class, path)` 组合：CUBE、VEC、TLSU 各自的
读和写。每条 lane 有自己的队列，所以某条读 lane 堵住，既拖不住写 lane，也拖不住别的类别。

**打标签。** 每条 lane 给请求盖上自己那个 `source_class`。lane 是编译期就定死的位置，所以
一个请求不可能被盖上别的类别的标签。

**算位置。** `bank = cell_key & BANK_INDEX_MASK`，`row = cell_key >> BANK_INDEX_BITS`。
按低位交织，拆分本身就是它的逆运算，所以一个 `cell_key` 只对应一对 `(bank, row)`。

**查行号。** `row >= ROWS_PER_BANK` 时置上 `out_of_range`。这只是报出来，不是动作：既不丢
请求，也不置故障，更不改道。

**往下传。** 记录里其他内容原样交给 [rq.md](rq.md)/[wq.md](wq.md)，只有那四个位置字段是新
写进去的。

整个解码就是组合逻辑的算术。每条 lane 加的那一级寄存器，就是这张卡片允许的那个可选流水线。

## 输入

| 名称 | 载荷/类型 | 含义 | 证据状态 |
| --- | --- | --- | --- |
| cube_read / vec_read / tlsu_read | CellReadReq | 一个 PE 里某个源类别发来的读请求，带代际限定，携带 `cell_key` 和身份，但不含位置信息 | 已实现 |
| cube_write / vec_write / tlsu_write | CellWriteReq | 一个 PE 里某个源类别发来的整 cell 写请求，带代际限定，其余同上 | 已实现 |

## 输出

| 名称 | 载荷/类型 | 含义 | 证据状态 |
| --- | --- | --- | --- |
| 解码后的读 lane，每个源类别一条 | CellReadReq | 还是那条记录，只是填好了 `source_class`、`bank`、`row`、`out_of_range`，交给 [rq.md](rq.md) | 已实现 |
| 解码后的写 lane，每个源类别一条 | CellWriteReq | 写这边是同样的形式，交给 [wq.md](wq.md) | 已实现 |

`bank` 和 `row` 都是 `u16`。原因是改字段时位宽必须完全一致，而前端又没有截断或转换的原语，所以只能跟 `cell_key` 表达式的位宽保持一致，尽管实际取值只要 3 bit 和 13 bit。映射 epoch 没做成字段，因为它归谁管还没定，在这里凭空加一个会造成状态重复。

提议表格中的载荷名称在字段、位宽和名义身份冻结前均为设计伪类型。Queue 传输由编译器推断，不应要求公开的 Queue 包装器。时钟/复位/时间域属于执行上下文，不得臆造为普通载荷端口。

## 所有或包含的状态

- 静态的作用域基址/范围表 —— **未展开**。参考实现解的是一整片扁平的交织空间，不查任何作用域表
- 静态 bank_groups、banks_per_group、rows_per_bank、mapping_mode —— **部分展开**。几何常量已经
  在共享契约里冻结、由 MAP 导入，但 `mapping_mode` 没有展开，目前唯一的解码方式就是低位交织
- 每条 lane 可选加一级流水线 —— **已展开**

MAP 不持有任何可变状态。解码是组合逻辑，所以这里没有一样东西是 Table 或持久变量。

## 参考实现

[`map.py`](map.py) 定义 `bgf_map_system`，每个 PE 展开一份。它接六条客户端 lane，每条 lane
打上 `source_class` 标签，从 `cell_key` 算出 `bank` 和 `row`，并给出行号有没有越界。记录
类型和解码用的几何参数放在 [`contracts/tmu_bgf.py`](../../contracts/tmu_bgf.py) 里共享，
因为这些字段是 MAP 写的、[arb.py](arb.py) 读的。

这个解码器是纯的：它只往记录上添位置字段，不改源身份，不丢请求，也不打乱 lane 的次序。
`bank` 是拿 `BANK_INDEX_MASK` 掩出来的，跑不出 `[0, BANK_PARTITIONS)`；下游在自己的 route
key 里又掩了一次，所以这个界是结构上成立的，不只靠 MAP 这边的承诺。

## 与卡片原设想的差异

有两处和这张卡片最初的提议不一样。

**解码是直接做在 lane 上的，不是一问一答的服务。** 原先设想的
`cell_map_req`/`cell_map_resp` 这一对端口，意味着请求得先存在别处，等解码结果回来再合到一起，
那 BGF 内部就要再搭一套队列。而这点运算本来就是组合逻辑，所以接口上直接把它挂在事务本身上。
每条 lane 加一级寄存器，就是这张卡片允许的那个可选流水线。

**作用域 base/range 表和 `mapping_mode` 都没有展开。** 这些几何参数本身还没定，而且它们需要
的查表也还没确认能做：用运行时的字段去索引一个静态元组降级不了，改字段又不接受截断，查表
结果的位宽必须和源表达式一致。所以这个配置只解码一种模式。

## 解码配置

**这个配置只解码一种模式。** `bank = cell_key & BANK_INDEX_MASK`，
`row = cell_key >> BANK_INDEX_BITS`，也就是按低位交织。作用域 base/range 表、
`mapping_mode`、Local/Shared 几何都还没定，所以没做。`BANK_PARTITIONS` 必须是 2 的幂：
`apply` 和 `route` 的表达式里有 `&` 和 `>>`，但没有 `%` 和 `//`。

**行数上限归 TRF 定。** `ROWS_PER_BANK` 是从 TRF 契约导进来的，
[bank.md](../trf/bank.md) 把它定成了 256。MAP 不能自己另写一个上限：BANK 会把每个行号掩码到
这个范围内，所以要是 MAP 用了另一个上限，就会出现 MAP 说"这行没越界"、BANK 却把它折到别的
cell 上的情况。这个上限远小于 `cell_key` 的取值范围，所以 `out_of_range` 是真的会发生的，
不会恒为假。不过 `out_of_range` 只是报出来，从不强制执行——谁负责拒绝，是下面的未决决策。

## 需验证的能力

- 静态/JIT 参数化的映射运算 —— 移位和掩码这一档**能用**；`%` 和 `//` 用不了，这就是几何参数
  必须取 2 的幂的原因。
- 带边界的数组查表、以及索引位宽的精确检查 —— **还没确认能不能做**。所以作用域 base/range 表
  没有实现：用运行时的字段去索引一个静态元组降级不了，而改字段又不接受截断，查表结果的位宽
  必须和源表达式一致。
- 可选的参数化流水线 —— **能用**；现在展开的配置每条 lane 用一级寄存器。

这些是待验证的要求，并不证明当前框架缺少相应能力。先测试当前修订版；确认缺口后，将其作为通用框架/原语问题加入回归，并先合入共享修复，再提交依赖设计的 PR。

## 行为验收

- 只有解码后的 lane 有空位时才收请求。lane 被堵住时请求留在原处，而且只对自己这个源类别施加
  反压
- 现在展开的这个配置是一对一的确定映射：一个 `cell_key` 只对应一个 `(bank, row)`，而低位交织
  本身就是它的逆运算
- 每条 lane 只打自己那个 `source_class`，请求不会跑到别的类别的 lane 上去
- `bank` 一定落在 `[0, BANK_PARTITIONS)` 之内，所以下游 route 的选择子不可能越界
- `out_of_range` 只在 `row >= ROWS_PER_BANK` 时置位。置位之后既不丢请求，也不改别的字段
- 就算被反压，映射也不会动源身份：它只写那四个位置字段
- 拒绝 Local PE 跨所有权访问、以及 Local/Shared 互相别名 —— **没做**；作用域表还没定，查表
  能力也还没确认

gfsim 执行是首个实现门槛。PYC/RTL 义务适用于获准的降级结果；拒绝临时存储的部分仍须明确后续工作。仅编译证据不能证明行为正确。
