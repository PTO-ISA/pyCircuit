# TMU.TRF.REF — 引用计数

- 源候选项： `DAV-TMU-TRF-REF-0001`
- 硬件层次： **H3**，位于 H1 `TMU` / H2 `TRF`
- NDF 细化： **L2 微架构**；模块级 L1 行为链接仍需评审。
- 建议处置： **叶节点**（提议，尚未获目录批准）
- 拟定实现路径（若接受为独立叶节点）：`designs/davincioo/tmu/trf/ref.py`
- 当前设计计划执行状态：**代码已实现，还没跑 gfsim 验证**。状态放在持久索引变量里，
  Decision 0151 把这种存储算作临时状态，PYC 和 RTL 必须明确拒绝它，所以目前只能跑 gfsim。
  另外有一条验收条件做不到，是框架限制，原因写在下面。

REF 记的是还有几个消费者拿着某个 Tile 版本，好让这块空间在还有人读的时候不被收回去。

## 它解决什么问题

一个 Tile 版本可能同时被好几个消费者在读。在最后一个读者读完之前，这块空间不能被回收。REF
就是记这个数的账本。

更要紧的是它**不**做什么：**它只数数，不做回收决定。** 引用归零只是"可以考虑回收了"的一个
信号，仅此而已。真要把空间收回去，还得有逻辑生命周期的许可，而那个 REF 看不到。

一个租约由 `(owner, tile_version, lease_kind)` 认。装它的槽号是 REF 内部怎么摆放的事，任何
响应里都不带。四种操作就把活全干了：获取、转移、释放，以及一个只读的查询。

## 在系统里的位置

一个 Tile 的生命周期被切给了好几个模块，各管一段。REF 只管"还有几个人在读"这一段：

| 谁 | 管什么 | 不管什么 |
| --- | --- | --- |
| [RAT](../trn/rat.md) | 逻辑名到版本号的映射 | 这个版本的数据在哪 |
| [FRE](../trn/fre.md) | 哪块物理空间空着、这个版本占了哪块 | 空间里装了什么 |
| [STS](../trn/sts.md) | 版本的描述符、写没写过、发布没发布 | 数据字节 |
| [BANK](bank.md) | 数据字节本身 | 这块空间归谁、什么时候能回收 |
| **REF** | **还有几个人正在读这个版本** | **有没有权限真的回收** |
| [LTR](../trn/ltr.md) | 把上面几家的动作串成一个有序事务 | 任何一份状态 |

所以 REF 既看不到数据，也看不到逻辑名，它看到的只是一个计数。真正释放槽的是 FRE，而 FRE 动手
之前需要两个结论：物理引用为零，这个 REF 能答；还有逻辑生命周期许可，这个 REF 答不了。能同时
拿到两个结论的是 [LTR](../trn/ltr.md)。

BGF 那一侧的事情跟这里完全不沾：[MAP](../bgf/map.md) 把 `cell_key` 解成 `(bank, row)`，
[ARB](../bgf/arb.md) 决定每个周期哪个源类别拿到某个 bank，[RQ](../bgf/rq.md) 和
[WQ](../bgf/wq.md) 给这些访问排队。那几家搬的是字节，REF 只管给读者记账。

## 一次操作怎么走完

三种变更操作从同一条流进来，靠 `operation` 字段区分。查询单独走一条流。

**获取。** REF 先按 `(owner, tile_version, lease_kind)` 找有没有这个租约。找到了就把计数加
一；没找到就占一个空行，计数置 1。所以同一个 owner 两次持有同一版本，结果是一行、计数为 2，
而不是两行——这同时也让"找租约"这件事不会有歧义：只有查不到时才会去占空行，所以任何时候最多
只有一个 live 行能匹配上这三个字段。计数已经到顶就不再加：计数要是回绕成 0，一个还在用的版本就会被当成可回收的，所以
宁可拒绝这次获取。

**转移。** `owner` 是就地改的。这正是"转移过程中不会出现没有主人的瞬间"的原因——那一行从头到
尾都在。要是把租约搬到另一行，恰好就会造出这个被禁止的瞬间。

**释放。** 计数减一。减到 0 时，这一行被标成不再 live，`release_pending` 置上，而这次完成会
走 reclaim 分支出去，不走普通的应答。重复释放不需要额外的比较就是安全的：查已有租约的条件里
带了 `live`，所以已经释放掉的租约，第二次根本查不到，自然什么都不会改。

**查询。** 由另一条只读 rule 处理，它读同一个账本、从不写，所以查到的是真实状态而不是副本，
也不用排在变更操作后面等。

每次变更都会产生一个应答，哪怕这次什么都没改，所以请求绝不会被静默丢掉。`accepted` 说账本有
没有真的改，`matched` 说这个租约在不在，`count` 是读到的当前计数。

但这几位分不开所有情况。账本满了、计数到顶了、释放一个根本不存在的租约，这三种都回
`accepted=False`。`matched` 能把"计数到顶"单独摘出来，可"账本满"和"租约不存在"都是
`matched=False`，而这两件事的含义完全不同。见未决决策。

## 输入

| 名称 | 载荷/类型 | 含义 | 证据状态 |
| --- | --- | --- | --- |
| request | LeaseRequest | 一次获取、转移或释放。看 `operation` 区分是哪种，用 `(owner, tile_version, lease_kind)` 找对应的租约 | 已实现 |
| query | RefcountQuery | 查某个 TileVersion 被引用了几次，不改任何状态 | 已实现 |

## 输出

| 名称 | 载荷/类型 | 含义 | 证据状态 |
| --- | --- | --- | --- |
| acknowledged | LeaseRequest | 三种变更操作的统一结果。`accepted` 说账本有没有真的改，`matched` 说这个租约在不在，`count` 是读到的当前计数 | 已实现 |
| reclaim | LeaseRequest | 把引用数减到 0 的那次释放。真要回收还得另外拿逻辑生命周期的许可，REF 自己不释放任何东西 | 已实现 |
| answered | RefcountQuery | 查询结果：`found` 有没有查到，`count` 引用几次 | 已实现 |

提议行中的载荷名称是设计伪类型，直至字段、位宽与名义身份冻结。队列传输由编译器推断，不是被请求的公开 Queue 包装器。时钟/复位/时域属于执行上下文，不得臆造为普通载荷端口。

## 所有或包含的状态

- 账本数组，`LEASE_SLOTS` 行，一行一个租约，只有一处会写它
- 每行存 owner、TileVersion、lease kind、引用计数、获取时的 epoch、release-pending、
  tombstone
- 不存任何数据字节，不存描述符，也不管生命周期——那不是 REF 的事

## 参考实现

[`ref.py`](ref.py) 定义变更规则 `serve_lease_request`、只读规则
`answer_refcount_query` 与系统 `trf_ref_system`。类型与冻结常量通过
[`contracts/tmu_trf.py`](../../contracts/tmu_trf.py) 共享。

账本就是一个数组，只有一处会写它，这是 Decision 0151 的硬要求。一行就是一个租约，`count` 是
它的引用数。

要干的活靠两次查表定位。找已有租约时，`live`、`owner`、`tile_version`、`lease_kind` 四个条件
必须同时成立，光某一个字段对上不算匹配。找空槽时，要求那一行既不是 live，也没有 tombstone：
带 tombstone 的行还有迟到的响应没排空，复用它会让一个排空的响应落到另一个租约上。

一条 rule 服务全部三种变更操作，这就是账本单端口的原因：一条 rule 每 tick 只收一个 token，
所以每周期最多一次变更打到数组上。应答流之后用一个普通 route 按 `outcome` 分开，所以等应答的
调用方和回收的消费者各自独立反压，互不影响。

## 与卡片原设想的差异

**三种操作合成一条流**，没按卡片原来设想做三个独立端口。这不是图省事，是只能这么做：
一条 rule 要等它的每个输入都来了 token 才触发（Decision 0167/0168），而获取、转移、释放
是各自独立到达的，做成三个端口就会互相干等，卡死。合成一条流其实也更接近真实硬件——账本
只有一个端口，一个周期本来就只处理一次操作。查询不改状态，所以单独走一条流，由一条只读
rule 处理。

**回收通知用的还是 `LeaseRequest`**，没另外定义类型。因为一条 rule 不能一边查表一边输出
多路结果：`ac.find` 配多输出前端就报错，Decision 0210 也把多路输出列为以后再做；而队列
transform 又改不了数据类型。所以改成在记录里标一位，再用 route 把它分出去。这样时序上反而
更准确——引用数归零本来就是那次释放当场的结果，同一个 tick 就能看到。

**响应里不带槽号。** 租约是靠 `(owner, tile_version, lease_kind)` 认的，槽号只是 REF 内部
怎么摆放的事，外面不需要知道。这跟 BANK 不对外暴露 cell 内部坐标是一个道理。

**`reclaim` 目前还没有消费者。** 引用归零只是 [fre.md](../trn/fre.md) 释放一个槽所需的两个
前提之一，另一个是逻辑生命周期许可，而那个 REF 看不到。能同时看到两者的是
[ltr.md](../trn/ltr.md)，它还没实现，所以这个输出现在是断头的。FRE 是最终的执行者，不是直接
的接收方。

## 已冻结的决策

卡片原先把 lease kind、表容量、计数回绕上界、求和方式这四项列为未决。实现时定成了这样：

| 决策 | 取值 | 理由 |
| --- | --- | --- |
| Lease kind | `LEASE_KIND_READ`、`LEASE_KIND_WRITE` | 只要还有写者拿着这个版本，就不能报回收，所以读和写分开计数 |
| 表容量 | `LEASE_SLOTS = 64` | 查空槽的逻辑不依赖具体行数，以后改这个值不用改代码 |
| 回绕上界 | `LEASE_COUNT_MAX`，到顶就不再加 | 计数要是回绕成 0，一个还在用的版本就会被当成可回收的。宁可拒绝这次获取 |
| 求和方式 | 不求和，一行一个租约 | 框架没有求和这类算子，所以按版本查询就是读一行。局限见"未决决策" |

## 后端边界

持久索引变量在 Decision 0151 里算临时状态，PYC/RTL 必须明确拒绝，所以目前只有 gfsim 能跑
这个模块。[bank.md](bank.md) 记了同一条边界，以及要怎么改框架才能去掉它。

## 需验证的能力

- 按条件查表并改字段 —— 能做。`ac.find` 带 `where`/`key` 找到一行，`with_fields` 换掉它
- 跨行的原子插入/自增/转移 —— 能做。两次写挂在同一个条件下，一起生效。转移其实不用动到
  第二行，理由见下
- 多路输出、要么全成要么全不成 —— **只能部分做到**。查表的 rule 没法同时输出多路，只好把
  结果用 route 分开
- 按代际条件把多行加起来 —— **做不到**，框架没有这类算子。一行一个租约的设计让常见情况用
  不上求和，但不是所有情况都能绕开，见"未决决策"
- PYC/RTL 的 Table 降级 —— 只要存储还算临时状态，就**按设计被拒绝**，见"后端边界"

这些是要求，不是当前框架缺失每一项的证明。先在当前修订版上测试；被证实的缺口应先成为通用框架/原语问题与回归，再提交依赖它的设计 PR。

## 行为验收

- 表满时应该让请求方等着，别接这个请求 —— **没做到**，见第一条未决决策。现在的做法是照样
  应答，但 `accepted=False`。请求不会丢，但请求方得自己重试
- 转移过程中不能出现"没有主人"的瞬间 —— **做到了**。owner 是就地改的，那一行从头到尾都
  在。要是把租约搬到另一行，恰好就会造出这个瞬间
- 重复释放只减一次 —— **结构上就成立**。幂等不是靠比较做出来的，而是查表条件里带了
  `live`：已经释放掉的租约，第二次根本查不到，自然什么都不会改
- 计数归零时报回收候选，但不真的释放逻辑版本 —— **做到了**。REF 的全部动作就是写账本和
  把结果分流出去，只有一处状态，没有任何释放路径
- 被取消的读要留住 tombstone，等迟到的响应都回来 —— **部分做到**。带 tombstone 的行不会
  被当成空槽，所以不会被复用。但谁来设置、谁来清除这个 tombstone，卡片里没有对应端口，
  见"未决决策"

设计本地证据：
[`test_ref_lease_ledger.py`](../../tests/fabric/test_ref_lease_ledger.py)。

gfsim 执行是首个实现门槛。PYC/RTL 义务适用于获准的降级结果；拒绝临时存储的部分仍须明确后续工作。仅编译证据不能证明行为正确。

## 未决决策

- **表满时没办法让请求方等着，这条验收做不到。** Decision 0210 规定 rule 吃不吃输入这件事
  必须由一个恒真的条件决定，而且明确说了：不输出的那条路径**照样会把输入吃掉**。所以"表满
  了"这种从状态算出来的条件，没法把请求留在队列里。现在只能总是应答、带 `accepted=False`，
  请求不丢但要重试。要真正解决，得让框架支持"消费与否由状态决定"，这是通用能力，该在上游
  做。测试里固定了现在的行为，等这个能力落地，那条断言就会失败，提醒回来改。
- **按版本查引用数，返回的是某一行的计数，不是几行加起来。** 如果多个 owner 同时持有一个
  版本，查询返回的是引用最多的那一行，而不是总和——框架没有求和算子。一行一个租约这个设计，
  对单个 owner 是对的，对共享的版本就是错的。要么上游保证不会出现共享，要么框架得提供求和
  能力，这两条都还没定。
- **一个 `accepted` 位分不开"资源不够"和"调用方搞错了"。** 账本满了、计数到顶了、释放一个
  根本不存在的租约，这三种都回 `accepted=False`。`matched` 能把"计数到顶"摘出来，但"账本满"
  和"租约不存在"都是 `matched=False`，而前者的意思是"待会儿再试"，后者的意思是"调用方错了，
  或者在重复发"。加一个独立的原因码就能分开，代价是共用的那份记录上多一个字段；至于到底哪些
  调用方真的需要分开，还没查清。
- **tombstone 没有谁来设置、谁来清除。** 这个字段是有的，也确实能让那一行不被当成空槽，
  验收要的就是这个效果。但卡片里没有任何输入端口负责在取消时把它置上，也没有端口在迟到
  响应都回来后把它清掉。得先确定取消和排空由谁负责，这条生命周期才算完整。
- `acquired_epoch` 算不算租约身份的一部分，还没定。现在它只是被记下来、获取时刷新一下，
  从不参与比较，所以 epoch 回绕暂时不会让两个租约混起来。
