# 通用 WSE 时序执行模型

`TimedWseMachine` 使用与功能版本相同的节点内存布局、路由和接收账本规则，
通过事件队列推进通信时间。输入仍是程序、原始数据和硬件配置；数据确实经过
源读取、网络传输完成和目的写回，WAIT 等到接收账本完成后才继续。

## 两种时间

- `model_time_noc_cycles`：模型中的片上网络时间，每周期 0.5 ns。
- `execution_cycles`、`host_cycles`、`timing.phases`：gfsim 求解的步数和电脑耗时。

维护事件堆、遍历节点、用共享功能内存搬运一份已到期的数据，可以花费多个
求解步骤。这些步骤保持模型时间不变，处理完当前事件后才推进到下一事件时刻。
因此，模型可以表达不同节点在同一硬件时刻完成传输。

## 程序与数据

新增 SEND 把一条 COPY 对应的数据作为一个独立包提交到源节点队列；旧 COPY
仍等待复制完成。BARRIER 等全部传输排空，消耗配置中的对齐与接收准备时间，
重新确定 Calendar 原点。AllGather 的行列划分及屏障由程序生成器给出。

默认配置保留 40 节点、每节点 64 KiB。每源有 8 个等待描述符、1 个活动包和
1 个注入 flit 暂存位置。路由分支使用各自的方向链路，未接收的分支继续等待；
源上一 flit 的首跳分支全部接受后，下一 flit 才能注入。
每条方向链路每网络周期传一个 64 B flit；端点每周期最多接收一个 flit。
当前包头条件下有效载荷为 52 B。每条 COPY 独立分包，不把一个源的八个片段合并。

源端整包读取后发送，目的端整包收到后写存储。每节点读写端口独立。
中间节点逐 flit 流水转发。Calendar 的时隙许可由加载的掩码决定，硬件不会
根据“AllGather 行阶段”等算法名称选择路径或放行时间。

## 参数与结果

参数文件为 `models/machine/timing_profile.json`。其中首拍 100 ns、存储每核
周期 128 B、单跳 1 个网络周期、时窗 1024 周期等仍标为 `pending`。
结果名称为“指定配置下的硬件模型预测时延”，目前没有硅片校准。

`events.jsonl` 保存有时间戳的执行事件。kind 1 是源读完成，2 是源 flit 注入，
3 是方向链路请求，4 是 flit 到达，5 是实际目的末拍提交，6 是包完成处理，
7 是 WAIT 完成，8 是 END，9 是端点接收尝试。请求及尝试可能因资源占用而重试，
不能把每条请求记录都算成已传输的 flit。事件6也可能等待尚未排空的分支。
`simulation.json` 保存模型时间和宿主机耗时；`verification.json` 保存校验及来源。

## 验收条件

小规模用例使用同一台 40 节点机器、默认暂定参数和开放 Calendar，分别检查
单跳、互不争用的并发链路、共享链路、分叉组播及两跳流水。两跳用例发送
200 B，形成四个 flit；预期第二个 flit 到达中继时，第一个已经到达目的节点。
这些预期由测试侧手算，机器只接收程序、数据和配置。

三个控制变量用例分别只改动单跳延迟、单条链路的 Calendar 许可、目的节点的
落地许可。完整 AllGather 使用 PTO 编译生成的 32 成员程序，逐字节比较输出，
并从实际事件检查行阶段写入先于列阶段读取。每次运行的通过情况以对应
`verification.json` 为准。
